# Platform Administration UI Strategy

**Status:** Accepted
**Date:** 2026-08-12
**Scope:** FRD-001 Volume-8 — Platform Administration UI. How `apps/admin` implements platform navigation, the platform permission system, Workspace Registry, Platform Users, Customer Support, Break-Glass, and Governance & Compliance on top of the frozen Platform Administration backend (PRD-007), as `apps/admin`'s first real screens beyond the Volume-1/Volume-2 scaffolding.
**Implemented in:** `apps/admin/src/{lib/permissions.ts,types/platform.ts,types/pagination.ts,services,features/platform,components/layout/platform-sidebar.tsx}`, `apps/admin/src/app/(platform)/{workspaces,platform-users,support,break-glass,governance}`, `packages/ui/src/components/{platform-user-card,support-ticket-card,break-glass-card,governance-card}.tsx`

## Platform navigation: flat, independent, `apps/admin`'s first real screens

`apps/admin` had zero real Platform screens before this volume — Volume-1/Volume-2 shipped only auth scaffolding and a placeholder dashboard route. `platform-sidebar.tsx` replaces that placeholder with a flat 12-item list (`PLATFORM_TABS`), matching §6's own flat structure rather than `apps/web`'s per-module `SidebarGroup` nesting — `apps/admin` is one console, not several tenant-facing modules with natural groupings. Each item is called through its own unconditional permission hook (never inside `.map()`, matching `apps/web`'s established discipline) and filtered into a `grantedPermissions` Set before rendering, so an item is hidden entirely rather than shown disabled or behind a 403 — the same "hide entirely" rule every `apps/web` volume has followed since Volume-2.

## Platform permissions: a fully independent system, not a shared hook

`lib/permissions.ts` introduces `usePlatformPermissionLevel`/`useHasPlatformPermission`/`useHasFullPlatformPermission`, the Platform Administration equivalent of `apps/web`'s `lib/permissions.ts` (FRD-001 Volume-3) — but deliberately never imports from it, never shares a hook, a Zustand store, or a permission enum with it (`ADR-PLAT-001`). It reads `PLATFORM_PERMISSION_MATRIX` via that matrix's own `getPlatformPermissionLevel`/`hasPlatformFullAccess` helpers rather than indexing the matrix directly, and computes "any access" as `level !== NONE` manually since no `hasAnyPlatformAccess` equivalent exists on the matrix module. Unlike Settings' binary `EDIT_WORKSPACE` (NONE/FULL only), several Platform permissions carry a genuine `VIEW_ONLY` tier — e.g. `MANAGE_ANNOUNCEMENTS` grants `PLATFORM_SUPPORT_EXECUTIVE` `VIEW_ONLY`, not `FULL` — so the read/write hook split is load-bearing here, not just defensive convention; every write action across all six screens this ADR covers gates on `useHasFullPlatformPermission`, never the read-only hook alone.

## Workspace Registry: Suspend/Reactivate/Archive, no actions from Archived

`workspace-registry-view.tsx` reuses the generic `Table`/`TableHeader`/`TableRow`/`TableHead`/`TableBody`/`TableCell` primitives (FRD-001 Volume-2) directly rather than a bespoke "WorkspaceRegistryTable," since a paginated status/search table needs nothing a Workspace-specific component would add. Suspend and Archive require an inline reason (matching `MANAGE_WORKSPACE_STATUS`'s own audit-trail expectation); Reactivate does not. The screen only offers Suspend/Archive from `ACTIVE` and Reactivate/Archive from `SUSPENDED` — no actions are shown from `ARCHIVED`, treated as a terminal state in the UI. This is a conservative choice, not a confirmed backend rule: the real archived-reactivation semantics were not fully verified against `WorkspaceStatusService`, and is filed as Technical Debt rather than guessed at.

## Customer Support and Break-Glass: one generic PATCH, no Reject

`support-view.tsx`'s Assign/Change-Status/Resolve/Close actions all route through `supportService.updateTicket()`, a single generic `PATCH` — no dedicated per-action routes exist on `SupportTicketController`. `break-glass-view.tsx` follows the Architect's explicit resolution that Break-Glass is Super-Admin-only end-to-end for the actions that grant live cross-tenant access (`APPROVE_SUPPORT_ACCESS`/`START_SUPPORT_SESSION`), while `REQUEST_SUPPORT_ACCESS` and both `VIEW_*` permissions are available to all three platform roles — and that a `REQUESTED` session can only ever be Approved, never Rejected, since no reject route exists anywhere on `PlatformBreakGlassController` (filed as Technical Debt). Once a session reaches `ACTIVE`, the screen offers a read-only Workspace Overview panel (`workspace`/`users`/`subscription`/`invoices`/`settingsOverview`) sourced from `breakGlassService.getWorkspaceOverview()` — this view never writes to tenant data; it is the real, gated "read-only tenant access" §4.6 describes, not a synthetic composition.

## Governance & Compliance: client-side padding, no Violations concept

`GET /platform/policies` only returns keys that have actually been `PATCH`ed at least once — a fresh system returns `[]`, with no seeded defaults. `governance-view.tsx` pads all 6 `GovernancePolicyKey` values client-side into an explicit "Unset" row (`GovernanceCard`'s `isSet={false}`, `version={0}`) rather than only rendering what the backend happens to return, since a Super-Admin auditing platform policy needs to see what has never been configured, not just what has. `VIEW_COMPLIANCE` gates a separate Compliance snapshot section entirely independent of Policies — no "Violations" field or concept exists anywhere on the backend (Architecture Review, 2026-08-12), so it is not represented in either section; runtime enforcement of policy values remains open Technical Debt (TD-024), unrelated to this read/write surface.

## Permission rendering: `useHasPlatformPermission`/`useHasFullPlatformPermission` throughout

Every one of the 12 Volume-8 screens follows the identical split: a view-gate hook determines whether the screen renders at all (hidden entirely, matching the sidebar's own discipline), and every write action independently gates on the full-access hook — verified screen-by-screen against `PLATFORM_PERMISSION_MATRIX` during the post-implementation Architecture Review pass, with no gaps found.
