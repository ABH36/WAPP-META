# Security Hardening Strategy

**Status:** Accepted
**Date:** 2026-08-13
**Scope:** PHD-001 Volume-1 (Security Hardening) — the first Production Hardening Document in this engagement, and the first volume to touch `apps/api` directly (every prior FRD volume was frontend-only). Covers the refresh-token cookie ownership migration, Platform Admin lockout parity, JWT hardening, and rate-limiting additions approved in the Architecture Review.
**Implemented in:** `apps/api/src/common/security/refresh-cookie.service.ts`, `apps/api/src/modules/{identity,platform,workspace}/controllers/*.ts`, `apps/api/src/modules/{identity,platform}/services/{auth,platform-auth,token,platform-token}.service.ts`, `apps/api/src/config/{configuration,env.validation}.ts`, `apps/web/src/{lib/api.ts,providers/auth-provider.tsx,features/auth/login-form.tsx}`, `apps/admin/src/{lib/api.ts,providers/auth-provider.tsx,features/auth/login-form.tsx}`, `packages/ui/src/index.ts`

## The centerpiece change: the backend, not the frontend, now owns the refresh-token cookie

Before this volume, `apps/web`/`apps/admin` received the refresh token in the JSON response body and mirrored it into a plain, JS-readable `document.cookie` themselves (`packages/ui/src/lib/cookies.ts`), purely so Next.js Edge middleware could check for its presence for route-gating. This is a real XSS-to-refresh-token-theft vector: any script-injection vulnerability, anywhere in either app, could read `document.cookie` and exfiltrate a live 30-day session token. This amends **ADR-FE-001**'s "backend never sets cookies" clause specifically for the refresh token — the access token's transport (JSON body, memory-only on the client) is unchanged, still never touches a cookie or `localStorage`.

The backend now sets a true `httpOnly` cookie via `Set-Cookie` on `login`/`refresh`/`verify-email` (and, discovered during implementation — see below), and every controller strips `refreshToken` out of the JSON response entirely: `IssuedTokenPair`/`IssuedPlatformTokenPair` (the internal, service-to-controller shape carrying the raw token) never reaches a controller's return value; only `AccessTokenIssued`/`PlatformAccessTokenIssued` (`{accessToken, expiresIn}`) does. `RefreshCookieService` (`common/security/`, alongside `TokenEncryptionService` as a `@Global()` primitive) centralizes the cookie's actual attributes — `httpOnly: true`, `sameSite: "lax"`, `secure` only in production, `path: "/"` — so every call site sets the identical cookie, not four independent copies of the same logic.

## A vulnerability discovered mid-implementation, not in the original approved scope, fixed anyway

`WorkspaceController.create` and `TeamController.acceptInvitation`/`transferOwnership` all call `AuthService.reissueTokens()` — minting a fresh session when a user's role or workspace membership changes — and were returning the full token pair, including the raw refresh token, directly in the JSON body, identical to the vulnerability this volume exists to close. This wasn't named in the Architect's approval (which reasonably focused on the login/refresh/logout endpoints), but it's the same vulnerability class at different call sites, not a new feature — deferring it would have left the exact hole this volume closes elsewhere still open. Fixed identically to `AuthController`: cookie set via `RefreshCookieService`, response body narrowed to `AccessTokenIssued`. This also broke 5 e2e specs whose test flow read the refresh token from response bodies (`auth`, `settings`, `workspace`, `golden-flow`) — all rewritten to read/replay the httpOnly cookie instead (`workspace.e2e-spec.ts`/`golden-flow.e2e-spec.ts` use `supertest` agents — real per-identity cookie jars — since they track two independent sessions, owner and member, across many sequential calls).

## "Remember Me" moved server-side, not resent on every refresh

Previously a pure client-side `localStorage` flag (`lib/remember-me.ts`, now deleted — dead code once nothing calls it) computing the cookie's own `Max-Age` on the client. The refresh flow no longer takes a request body at all in the cookie-based design, so resending the flag on every refresh isn't an option. Instead, `rememberMe: boolean` is persisted once on the `Session`/`PlatformSession` document at login (from `LoginDto`/`PlatformLoginDto`'s new optional field — the login form already had a real "Remember Me" checkbox collecting this value and silently discarding it; this closes that gap) and automatically carried forward through the rotation chain: each `refresh()` reads the _old_ session's `rememberMe` and applies it to the newly-rotated session, so the client never needs to know or resend it. `false` → session cookie (`Expires` omitted, cleared when the browser closes); `true` → `Expires` set from `TokenService.signRefreshToken()`'s own real `expiresAt`, not a separately-maintained duplicate constant.

## Cross-origin cookie scoping: read from `docker/nginx/nginx.conf`, not assumed

`apps/api` is reverse-proxied under `apps/web`'s own origin in production (`location /api/`) — same-origin, so `apps/web` needs no `Domain` cookie attribute at all. `apps/admin` is a genuinely separate subdomain (`server_name admin.wapp.example`) and _would_ need `Domain=.wapp.example` for its own middleware's presence-check to keep seeing the cookie. Rather than hardcode a guessed production domain, `COOKIE_DOMAIN` is a new, optional, environment-driven config value (`configuration.ts`/`env.validation.ts`) — unset in dev (host-only cookie is sufficient; RFC 6265 scoping ignores port, so `localhost:3000`/`3001`/`4000` already share host-only cookies automatically), required only in production for `apps/admin`.

## What the frontend migration actually removed, not just changed

Once the backend owns the cookie, the client-side mirroring code that existed solely to serve middleware's presence-check becomes provably dead: `packages/ui/src/lib/cookies.ts` (`getCookie`/`setCookie`/`deleteCookie`) and `remember-me.ts` in both apps are deleted outright, not deprecated-in-place — confirmed via grep that every consumer was one of the files being rewritten in this same change, with zero remaining call sites afterward. `AuthProvider`'s hydration flow changes in a way worth being explicit about: it previously read `getCookie(REFRESH_TOKEN_COOKIE)` before attempting a silent refresh, skipping the network call entirely when absent; an httpOnly cookie can't be read from JS at all, so every fresh page load now unconditionally attempts one silent refresh, treating a 401 (no cookie, or an expired/revoked one) as `unauthenticated` — the standard pattern for httpOnly-cookie-based session bootstrap. `middleware.ts` in both apps needed **zero code changes** — `request.cookies.has()` runs server-side (Next.js Edge middleware), which can see httpOnly cookies exactly as before; only the frontend's own JS-side reads were the problem.

## Platform Admin account lockout parity

The tenant `AuthService` already had brute-force lockout (`failedLoginAttempts`/`lockedUntil` on the `User` schema, an atomic increment-then-lock repository method) — `PlatformAuthService` had no equivalent, a real asymmetry in an admin-facing auth boundary that should be at least as hardened as the tenant one. Mirrors the tenant implementation exactly: same fields added to `PlatformUser`, same atomic `registerFailedLogin()` pattern, same shared `auth.maxFailedLoginAttempts`/`accountLockoutMinutes` config (deliberately the same values/config keys as the tenant side, not a separately-tunable platform threshold — no approved reason for platform admins to have a different brute-force tolerance than tenant users).

## JWT algorithm pinning and the platform/tenant secret boundary

`signAccessToken`/`signRefreshToken`/`verifyAccessToken`/`verifyRefreshToken` (both `TokenService` and `PlatformTokenService`) now pass an explicit `algorithm: "HS256"` / `algorithms: ["HS256"]` rather than relying on the library default — closes the theoretical `alg: "none"`/algorithm-confusion class of attack, defense-in-depth given HS256 was already the only algorithm ever used here. Separately, `env.validation.ts`'s `validateEnv()` gained a genuine boot-time check (not just a code comment, as it was before this volume) that all four JWT secrets (`JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `PLATFORM_JWT_ACCESS_SECRET`, `PLATFORM_JWT_REFRESH_SECRET`) are pairwise distinct — a misconfigured deploy that accidentally shares a signing key across the tenant/platform trust boundary now fails to boot instead of silently running with a forgeable cross-boundary token.

## Rate limiting: closing the one unthrottled credential-issuing endpoint, plus a new money-moving-action tier

`reset-password` was the one endpoint in `AuthController` without `@Throttle()`, despite carrying the same guessable-token brute-force risk as every sibling endpoint (`login`/`register`/`forgot-password` all already had it) — brought in line at the same 5/min tier. `PaymentController`'s `payments`/`refunds` endpoints (owner-authenticated, permission-gated, but otherwise only bounded by the app-wide 300/min default) gained a dedicated 10/min tier — a compromised or scripted Owner session shouldn't be able to hammer money-moving actions at the same rate as read-only browsing.
