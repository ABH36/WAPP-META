# Production Security Configuration

**Status:** Accepted
**Date:** 2026-08-13
**Scope:** PHD-001 Volume-1 (Security Hardening) — the production-facing configuration decisions that don't belong in ADR-PHD-001's cookie/auth narrative: frontend HTTP security headers, the dependency-vulnerability remediation posture, and the supply-chain (SBOM/image-signing) position for this volume.
**Implemented in:** `apps/web/next.config.ts`, `apps/admin/next.config.ts`, `pnpm-workspace.yaml`, `docs/DEPENDENCY-AUDIT-phase1.md`, `docs/TECH-DEBT.md`

## Frontend HTTP security headers: a real gap, not a duplicate of the backend's

`apps/api/src/main.ts` already configures Helmet with a real CSP/HSTS/`frameguard: deny` — but this only ever protected the API's own JSON responses. The actual HTML/JS/CSS `apps/web`/`apps/admin` serve had zero security headers before this volume; Next.js applies none by default. Both apps' `next.config.ts` gained an `async headers()` returning the same header set for every route: `Strict-Transport-Security` (`max-age=31536000; includeSubDomains`, matching the backend's own HSTS value), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera/microphone/geolocation all disabled — nothing in either app uses any of these browser APIs), and a `Content-Security-Policy`.

The CSP's `script-src 'self' 'unsafe-inline'` is a deliberate, documented tradeoff, not an oversight: Next.js's own hydration bootstrap injects an inline `<script>` tag, and this app has no nonce-based CSP wiring (which would require per-request middleware generating and threading a nonce through every page render — a substantially larger change than a hardening-volume header addition). This mirrors the exact same tradeoff the backend's own Helmet config already documents for `style-src 'unsafe-inline'` (Tailwind's dev-mode injection) — not a new class of accepted risk, the same one already reviewed and accepted elsewhere in this codebase. `connect-src` includes the real API origin, read from `NEXT_PUBLIC_API_URL` at build/start time (`new URL(...).origin`, so the DTO-style path suffix like `/api/v1` is stripped correctly) rather than hardcoded, so it resolves correctly in both dev (`http://localhost:4000`) and production (wherever the real API origin is) without guessing at an unapproved production value.

Verified by building both apps to completion (compiled successfully, all static pages generated — the one build-step failure encountered, `EPERM` on a symlink during standalone-mode trace-file copying, is a pre-existing Windows-only limitation unrelated to this change; Docker/Linux builds don't hit it) and by starting each in production mode and confirming every header above is actually present via `curl -D -`, including `connect-src` resolving to the real configured API origin.

## Dependency remediation: two criticals closed, everything else re-reviewed and re-documented

A fresh `pnpm audit` at the start of this volume found 61 advisories (2 critical, 22 high, 24 moderate, 5 low) — the existing `docs/DEPENDENCY-AUDIT-phase1.md` was 5+ months stale (dated 2026-08-04, before every FRD volume since) and no longer an accurate picture of the dependency tree. Both criticals this time were dev/build-tooling, not a production framework like Phase-1's `next` finding:

- **`vitest` <3.2.6** (arbitrary file read via its own UI server, dev-only) — bumped `^2.1.4` → `^3.2.6` across all 4 packages that use it. A major-version jump, so treated with the same weight as one: full test-suite re-run per package (`apps/web` 63/63, `apps/admin` 11/11, `packages/ui` 162/162, `packages/shared-validation` 13/13), typecheck, and a production build of both Next.js apps, all before accepting it.
- **`tar` <=7.5.18** (decompression DoS), reachable only transitively via `bcrypt → @mapbox/node-pre-gyp → tar`'s install-time prebuilt-binary extraction — confirmed via grep that no application code imports `tar` directly, unlike the `zod` phantom-dependency incident `ADR-FE-018` documents, where a blanket override broke a package that _did_ have its own explicit pin. A `pnpm-workspace.yaml` `overrides: { tar: ^7.5.19 }` resolves this safely; verified `bcrypt`'s native module still builds and a real hash/compare round-trip still works afterward.

Result: **0 critical**, down from 2. The full remaining-findings review (multer's unreachability, nodemailer's usage narrowed to connection-testing only and never `sendMail()`, the various dev/build-time-only findings, the NestJS 10→11-gated findings) is recorded in `docs/DEPENDENCY-AUDIT-phase1.md`'s new dated section rather than duplicated here — that document is the durable, evolving audit record; this ADR is the decision record for _how_ this volume approached it.

## Supply-chain (SBOM/image-signing) position for this volume: documented gap, not built here

The Docker/CI-CD/supply-chain research performed as part of this volume's own planning confirmed: no SBOM (Software Bill of Materials) is currently generated for any built image, and no image-signing (e.g., Sigstore/cosign) exists anywhere in the CI pipeline or `docker/` configuration. This is a genuine gap, not something already covered elsewhere — but building the actual mechanism (choosing an SBOM format/tool, wiring image signing into CI, choosing a verification policy at deploy time) is Docker/CI-CD infrastructure work, and this document's own roadmap footer already names **PHD-001 Volumes 2–4** as the sequence covering `apps/api`/Docker/CI-CD/Deployment Configuration specifically — Volume-1's approved scope was security hardening at the application layer (auth/cookies/headers/rate-limiting/JWT), not supply-chain infrastructure.

Consistent with this engagement's standing discipline of documenting a gap explicitly rather than silently deferring it: SBOM generation and image signing are recorded here as **known, accepted-for-now Technical Debt**, not overlooked. Closing this out looks like a future PHD-001 volume (or a dedicated CI/CD hardening pass) that selects a concrete SBOM tool (e.g., `syft`) and signing mechanism (e.g., `cosign` keyless signing via the CI provider's OIDC identity) and wires both into the existing Docker build/publish pipeline — not something to invent unapproved tooling choices for here.
