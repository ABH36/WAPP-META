# Communication Inbox Strategy

**Status:** Accepted
**Date:** 2026-08-11
**Scope:** FRD-001 Volume-4 §4.2/§4.3/§4.4/§10/§11/§13 — the Inbox and Conversation View specifically: real-time model, conversation/message presentation, the Message Composer's 24-hour compliance-window handling, and the permission-rendering rules applied across the entire Communication surface.
**Implemented in:** `apps/web/src/features/communication/{inbox-list,inbox-split-view,conversation-view,message-composer}.tsx`, `apps/web/src/lib/{permissions,template-placeholders}.ts`

## Real-time is polling-only, because no push mechanism exists at all

Confirmed by a repo-wide search during Architecture Review: zero matches for `WebSocketGateway`, `socket.io`, `EventSource`, or any gateway file anywhere in `apps/api`. Every domain event relevant to a live inbox (`CONVERSATION_ASSIGNED`, `MESSAGE_SENT`, etc.) is emitted via NestJS's in-process `EventEmitter2` and consumed only by a logging listener — nothing is pushed to a client. Resolved via `AskUserQuestion` (Recommended): `inbox-list.tsx`/`conversation-view.tsx` use TanStack Query's `refetchInterval` (15 seconds) as an explicit, documented MVP compromise. No client-side WebSocket/SSE workaround was built to simulate push — that would have meant inventing a capability the backend doesn't have, which this engagement's standing rule (`ADR-FE-001`'s "no unsupported backend behaviour is simulated in the frontend") exists to prevent. See `docs/TECH-DEBT.md` for the real fix (a backend WebSocket/SSE layer).

## Desktop split-view is a real requirement (§13), not decorative — `InboxSplitView` layers it on top of the direct route

§13 explicitly names "Desktop: Split View — Conversation List + Chat" and "Mobile: Full-screen Conversation." `inbox-split-view.tsx` renders both panels side-by-side above the `lg` breakpoint (list on the left driving `ConversationView` inline via local state, no full navigation), and falls back to the plain list-only view below `lg`, where selecting a conversation navigates to the real `/communication/conversations/:id` route instead. That route stays fully functional and directly linkable on every viewport — the split view is additive, not a replacement, so a shared/bookmarked conversation link still works identically regardless of how the user arrived.

## Conversation status: `NEW` is excluded from the manual status dropdown; `getById` has a real contact-population gap

`NEW` is system-only — a manual `PATCH .../status` to `NEW` is rejected server-side (400). `conversation-view.tsx`'s status `Select` only lists the seven manually-settable values (`OPEN` through `ARCHIVED`), falling back to displaying the conversation's actual status as a disabled option if it's ever something else. Separately: `GET /conversations/:id` does not populate `contactName`/`contactPhoneNumber` (the list endpoint does — confirmed by reading `ConversationRepository.findById`, which has no `.populate()` call, versus `.list()`, which does). This is a real backend discrepancy, not a frontend bug — `ContactCard` simply shows its own "Unknown contact" fallback rather than attempting a client-side workaround (e.g., scavenging the Inbox's cached list data), which would only mask the gap for one render before the next poll cycle overwrote it with the broken data again. Filed in `docs/TECH-DEBT.md`.

## Message Composer: the 24-hour compliance window is handled reactively, not proactively — the field it would need isn't exposed

The backend's own compliance docs (`docs/COMM-COMPLIANCE-ENGINE.md`) explicitly name proactive UI warning as "a frontend concern once a frontend exists... today the API simply returns a clear 403," naming this volume as exactly the place to build it. During implementation, though, the field the compliance check actually uses — `Conversation.lastCustomerMessageAt` (distinct from `lastMessageAt`, which includes outbound messages too) — was found to exist on the Mongoose schema but is **not serialized** into `ConversationSummary` anywhere (confirmed against both the mapper and the type definition). There is consequently no client-side field to proactively check. `message-composer.tsx` instead catches the 403 reactively: a failed free-text send that returns `statusCode === 403` (the only realistic 403 source for this route, since `REPLY_CONVERSATIONS` is already required to reach the Composer at all) surfaces a warning with a one-click switch to the Template tab — matching the backend's own documented intent for the outcome, just triggered after the attempt rather than before it. Filed in `docs/TECH-DEBT.md` as the concrete fix (expose `lastCustomerMessageAt`, or a computed `withinCustomerServiceWindow` boolean, on `ConversationSummary`).

## Message status is 100% server-driven; "Sending" is the one purely client-side, optimistic value

`MessageStatus` has 8 real values (`QUEUED, SENT, DELIVERED, READ, FAILED, RECEIVED, PROCESSED, VISIBLE`) — `QUEUED` is defined but never actually returned today, since sends are synchronous and a message is already `SENT` by the time the API responds. `ChatBubble` accepts an optional `"SENDING"` status purely for the Composer's own in-flight UI state (a spinner icon while the POST is outstanding) — this value never comes from the backend and is discarded the moment a real response (or error) arrives; no message is ever persisted or refetched with that value.

## Permission rendering: `FULL` vs. "not `NONE`" is a real, enforced distinction, not just a style choice

The Architect's approval was explicit: "Write actions must require FULL permission. View-only users shall never receive create, edit or send actions." This matters concretely here because the backend's permission guard (`permissions.guard.ts`) only checks `level !== NONE` — it does not itself distinguish `VIEW_ONLY` from `FULL`, so a `SALES_MANAGER` (`VIEW_ONLY` on `CREATE_BROADCAST`/`CREATE_TEMPLATES`/`MANAGE_TEMPLATES`) is not actually blocked server-side from calling those write routes directly. `lib/permissions.ts` gained `useHasFullPermission` (checks `=== FULL`) alongside the existing `useHasPermission` (checks `!== NONE`) specifically for this volume; every create/submit/send/pause/resume/cancel action in Communication uses the `FULL` check, while every read/view gate uses the plain `useHasPermission` check. This is flagged as a backend-hardening item worth its own attention (`docs/TECH-DEBT.md`) independent of this frontend volume — the frontend gate is real and correct, but it isn't a substitute for the backend also enforcing the distinction.

Two inverse-access patterns recur throughout Communication and are each handled with independent, per-feature gates rather than one coarse switch:

- `ASSIGN_CONVERSATIONS` is stricter than `REPLY_CONVERSATIONS` — `SALES_EXECUTIVE`/`SUPPORT_EXECUTIVE` can use the Inbox but cannot assign; the Assign control checks its own permission separately from the screen-level gate.
- `MARKETING_EXECUTIVE` has zero Inbox access (`REPLY_CONVERSATIONS`/`ASSIGN_CONVERSATIONS`/`ADD_INTERNAL_NOTES` all `NONE`) but full Templates/Broadcasts/Campaigns access — the exact inverse of `SALES_EXECUTIVE`/`SUPPORT_MANAGER`/`SUPPORT_EXECUTIVE`, who can use the Inbox but are `NONE` on Templates/Broadcasts/Campaigns entirely. Every list/detail screen (`InboxList`, `ConversationView`, `BroadcastList`/`Detail`, `CampaignList`/`Detail`, `TemplateList`) independently checks its own read permission and renders an access-restricted message rather than firing a request that's guaranteed to 403 — the same "hide entirely" pattern `ADR-FE-005` established for Workspace's Branding/Preferences tabs, applied here because these underlying `GET` routes are themselves permission-gated, not just their writes. `MessageComposer`'s Template mode is hidden specifically for the three Inbox-capable-but-`VIEW_TEMPLATES`-`NONE` roles, since it's reachable from a screen those roles otherwise have full access to.

## A pre-existing `@wapp/shared-types` drift was found and deliberately not "fixed" from this volume

`ConversationStatus`/`TemplateStatus` in `@wapp/shared-types` don't match what `apps/api`'s Communication module actually returns (`PENDING_CUSTOMER` vs. the real `PENDING`; `SUBMITTED` vs. the real `PAUSED`), and `CampaignStatus`/`MessageStatus`/`MessageDirection`/`AssignmentStrategy` have no shared-package equivalent at all — the Communication module defines all of these locally rather than importing the shared package that (per its own doc comments) was seemingly meant to be canonical. `apps/web`'s own types (`types/conversation.ts` etc.) mirror the real, running backend instead, and `packages/ui`'s `getStatusColor` was extended with the real string values directly (see `docs/ADR-FE-007-communication-ui-strategy.md`'s sibling — actually captured in `packages/ui/src/lib/status-color.ts`'s own comment) rather than trusting the drifted enum. Reconciling `@wapp/shared-types` itself is out of this frontend volume's authority — it's a shared package other, non-Communication code may already depend on — and is filed as its own Tech Debt entry rather than silently patched.
