# COMM-008 — Campaign Scheduling Strategy

**Status:** Accepted
**Type:** Future architecture (documentation only — no implementation required by this ADR)
**Date:** 2026-08-05
**Raised by:** Architecture Review (Phase-4 Part-3b-ii recommendation #1)

## Current state — independent-timestamp waves, not a real dependency chain

Each Campaign wave (`docs/COMM-CAMPAIGN-LIFECYCLE.md`) is a standalone `Broadcast` with its own `scheduledAt`, enqueued as its own independent BullMQ delayed job at Campaign creation time. Nothing about wave 2 knows wave 1 exists — they just happen to share a `campaignId` and (usually) later timestamps. What reads as "sequential" today is really "each wave has its own clock, and the clocks happen to be set in order." This ADR names that plainly and defines the three genuinely different scheduling models a future Campaign might need.

## The four models

| Model                   | What it means                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Status                                                                                                                                                                                                                                                                    |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Sequential Waves**    | Today's actual behavior, named precisely: independently-timestamped waves with no runtime relationship to each other. Works today because nothing requires wave 2 to know wave 1's outcome — it just has a later `scheduledAt`.                                                                                                                                                                                                                                                                                                              | **Implemented**, as described above (not a true dependency chain — worth not overstating this in product copy).                                                                                                                                                           |
| **Parallel Waves**      | Multiple waves deliberately sharing one `scheduledAt` (or close enough to be simultaneous), grouped as an explicit product concept — e.g. an A/B content test, where two message variants go to two halves of the audience at the same moment specifically to compare performance. Nothing technical prevents two waves sharing a timestamp today (each wave is an independent job either way), but there's no product-level concept of "these waves are a parallel test group," no audience-splitting between them, and no comparison view. | Not implemented. Needs: per-wave audience subsets (today every wave gets the _entire_ Campaign's `targetContactIds`), and a "compare these waves" analytics view once `docs/ADR-COMM-009-campaign-analytics-strategy.md`'s hierarchy exists to compare against.           |
| **Conditional Waves**   | A wave's audience (or whether it fires at all) depends on a prior wave's outcome — e.g. "send Wave 2 only to recipients who didn't read Wave 1." Requires reading Layer 2 delivery/read data (`docs/ADR-COMM-007-broadcast-progress-strategy.md`) as an input to building the _next_ wave's recipient list, which today is fixed entirely at Campaign creation time.                                                                                                                                                                         | Not implemented — the biggest lift of the three, since it means wave creation can no longer all happen upfront in one `CampaignService.create()` call; a conditional wave's `BroadcastRecipient` list can only be computed once its prerequisite wave's outcome is known. |
| **Recurring Campaigns** | The same wave (or wave sequence) fires repeatedly on a schedule (e.g. "every Monday") rather than once. Doesn't fit today's `ACTIVE → COMPLETED` model at all — a recurring Campaign never legitimately reaches `COMPLETED` while still recurring, so it needs its own status semantics, not a variant of the current one.                                                                                                                                                                                                                   | Not implemented — likely a distinct concept ("Campaign Template" that spawns fresh one-off Campaign instances on a cron schedule) rather than a new status value bolted onto the existing `Campaign` schema.                                                              |

## Why this wasn't designed further now

Per the Architect's framing, non-blocking and documentation only. Parallel and Conditional waves both depend on capabilities not yet built (per-wave audience subsets; Layer 2 delivery data respectively) — designing their exact mechanics now would be speculative. This ADR exists so the _shape_ of the eventual work is named and sequenced correctly (Parallel needs audience subsets first; Conditional needs Layer 2 first; Recurring is architecturally separate from both) rather than each being designed independently whenever it's picked up.

## What this ADR does not do

No new scheduling model is implemented by this document. `Broadcast.scheduledAt` and the independent-BullMQ-job model remain exactly as `docs/COMM-BROADCAST-LIFECYCLE.md` and `docs/COMM-CAMPAIGN-LIFECYCLE.md` already describe.
