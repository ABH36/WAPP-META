# Monitoring Strategy

**Status:** Accepted
**Date:** 2026-08-13
**Scope:** PHD-001 Volume-2 (Observability, Monitoring & Logging) — the Prometheus metrics surface (every named business/infrastructure metric from the planning document), health checks, and the Diagnostics endpoint extension. Covers the "how do we measure what's happening" half of the volume; distributed tracing/correlation/logging is ADR-PHD-003.
**Implemented in:** `apps/api/src/common/metrics/*`, `apps/api/src/health/health-check.service.ts`, `apps/api/src/infrastructure/queue/queue-status.service.ts`, `apps/api/src/modules/settings/services/diagnostics.service.ts`, business-domain service files across every module (see §4.3 metric-by-metric list below)

## `prom-client` on one shared `Registry`, not a metrics-per-module split

`MetricsService` (`@Injectable()`, `@Global()` via `MetricsModule`) owns one `Registry` and every named `Counter`/`Histogram`/`Gauge` from the planning document's §4.3 as its own instance fields, registered to that single registry. `collectDefaultMetrics({ register: this.registry, prefix: "wapp_" })` gets Infrastructure's CPU/Memory/Event-Loop metrics for free — standard `prom-client` behavior, no hand-rolled Node process instrumentation needed. `GET /metrics` (`MetricsController`) serves `this.metricsService.registry.metrics()` in Prometheus text-exposition format — provider-neutral by construction: any scraper that speaks that format works, not specifically Prometheus itself, and no Prometheus _server_ is deployed as part of this volume.

The Architect's decision (of the 4 frozen design questions this volume) was to build every named metric as literally specified, not a prioritized subset — Auth, Communication, CRM, Billing, Settings, Platform, Infrastructure, Queue Observability, and Security Event Logging are all present on the registry, each wired to the exact service-layer call site that represents that event, not inferred from adjacent code.

## Cardinality discipline: never `workspaceId`, always the parameterized route

`MetricsService`'s own doc comment states the rule directly: no metric anywhere in this file is ever labeled by `workspaceId`. A label whose cardinality grows with the tenant count is exactly how a Prometheus-style time-series backend degrades — workspace-level detail belongs in logs/traces/audit records (see ADR-PHD-003), which don't share that constraint. `HttpMetricsInterceptor` reads `request.route.path` (Express's own parameterized-route pattern, e.g. `/workspaces/:id`) rather than the literal request URL, for the identical reason applied to a different axis — cardinality stays bounded by the number of route definitions, not by how many distinct resource IDs are ever requested.

## `MetricsAuthGuard`: a static bearer token, compared in constant time

A Prometheus-style scraper can't perform an interactive JWT login, so `GET /metrics` is `@Public()` (bypasses the global JWT guard) but gated behind `MetricsAuthGuard` — a static, config-time shared secret (`METRICS_AUTH_TOKEN`, required at boot via `env.validation.ts`, never defaulted to a guessable value) checked via `crypto.timingSafeEqual` after a length-equality guard, not `===`. A naive string comparison leaks the token's correct prefix length through response-time differences — the standard class of vulnerability keyed/secret comparisons need to guard against, and `@Public()` alone (no bearer-token gate at all) would have left the endpoint's own doc comment's constraint — "must never be publicly accessible" — unmet, since `@Public()` only means "skip the JWT guard," not "skip authentication entirely."

## Business-domain metrics: one `.inc()`/`.observe()` per already-existing domain-event emission site, not new code paths

Every business-domain counter is placed at the exact call site that already emits the corresponding domain event (or, where no event exists, the exact call site that would emit one) — never inferred from a method's name or a guess at "probably where this happens." A representative sample of the judgment calls made module by module:

- **Auth** — `authLoginFailureTotal`'s unknown-email branch is a standalone increment in `AuthService.login()`, not routed through `recordLoginAttempt()`, because that method's own doc comment already establishes it's deliberately not called for an unknown email (no `userId` to attribute the attempt to). `PlatformAuthService` centralizes success/failure into `recordLoginAttempt()` itself instead — a cleaner design than the tenant side, verified against the platform login method's actual control flow, not assumed to mirror tenant's shape simply because they're both "login."
- **CRM** — `crmLeadConversionsTotal`/`crmDealsCreatedTotal` both increment in `LeadConversionService.convert()`'s single success path, confirmed via reading `deal.repository.ts`'s only call site (there is no standalone deal-creation route — every Deal in this codebase originates from lead conversion).
- **Billing** — `billingPaymentsTotal{outcome}` increments in `PaymentService.record()`'s PAID/FAILED branches, placed immediately after each branch's existing `PAYMENT_PAID`/`PAYMENT_FAILED` event emit (same ordering the events themselves already use, not a new ordering decision).
- **Settings** — `settingsWebhooksTotal{action:"deleted"}` is the one metric in this volume with no corresponding domain event: `WebhookService.delete()` never emitted a `WEBHOOK_DELETED` event before this volume (confirmed absent from `domain-events.ts`) and none was added — the metric-only, no-new-event choice mirrors the Security Event Logging precedent (ADR-PHD-003) rather than inventing a new event on a hunch that one "should" exist.
- **Platform** — `platformBreakGlassTotal{action}`'s two label values are literally `"requested"`/`"approved"` per the metric's own declared label set; `start`/`end` in the Break-Glass lifecycle are intentionally _not_ instrumented here, since the metric's own doc comment scopes it to those two lifecycle events only. `platformWorkspaceSuspensionTotal{action}` covers `suspend()`/`reactivate()` only — `archive()` is a third, distinct lifecycle action the metric was never scoped to include.

## Infrastructure: the gauge lives inside the check, not bolted on afterward

`infraDependencyUp{dependency}` is set from _inside_ `HealthCheckService.checkDatabase()`/`checkRedis()` themselves, not from a separate call site that re-derives the same boolean. Both methods are the single shared implementation already used by both `/health` (unauthenticated, database-only, for container/orchestrator probes) and the authenticated `/settings/diagnostics` (the fuller check set) — per the Architecture Review's "extend through composition, not a parallel monitoring implementation" resolution already established for that shared service. Setting the gauge at the source means every caller of either check — present or future — keeps the gauge accurate for free, rather than requiring every future call site to remember to also update a metric.

## Diagnostics extension: a monitoring client scoped to queue _names_, not a cross-module DI reach

The Diagnostics endpoint needed build version/git commit/environment (already available via `configuration.ts`'s `observability` block from Volume-1's own build-time stamping), feature flags (a direct reuse of `FeatureFlagsService.list()`, already workspace-scoped exactly like the endpoint itself), cache status, and per-queue status/active-worker counts.

Queue status was the one genuine design decision. Every BullMQ `Queue` instance in this codebase is registered via `BullModule.registerQueue()` inside its _owning_ module (Billing/Communication/Platform/Settings/Infrastructure's email module) — those DI tokens live inside each module's own provider graph. Reaching into them from `DiagnosticsService` (owned by Settings) would mean either exporting BullMQ tokens across module boundaries or importing business modules into a shared/global one — both cut against the module-ownership boundaries this codebase enforces elsewhere (the event-driven integration standard exists for exactly this reason: business modules don't reach into each other's internals directly).

`QueueStatusService` (`infrastructure/queue/`) sidesteps this by holding its own standalone `Queue` client handles — one per queue, constructed directly via `new Queue(name, { connection })` using the same shared Redis connection URL every producer already uses — rather than injecting each module's DI-registered instance. This is a read-only _monitoring_ client scoped to plain string name constants (imported from each module's own `*.constants.ts`, which are just string literals with no service dependencies — safe to import across module boundaries the same way `DomainEvent` names already are), not a service-to-service call. `getStatus()` calls `getJobCounts()`/`getWorkersCount()` per queue; `onModuleDestroy()` closes every handle cleanly. Registered on the already-`@Global()` `QueueModule`, so it's available to `DiagnosticsService` (or anything else) without further wiring.

`activeWorkers` in the Diagnostics response is the sum of every queue's own worker count, not a separately-tracked figure — computed once, at read time, from the same `QueueStatusService.getStatus()` call the per-queue breakdown already needed.
