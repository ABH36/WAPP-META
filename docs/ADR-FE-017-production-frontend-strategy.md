# Production Frontend Strategy

**Status:** Accepted
**Date:** 2026-08-12
**Scope:** FRD-001 Volume-9 — Performance, Accessibility & Progressive Web App. How `apps/web`, `apps/admin`, and `packages/ui` were hardened for production: accessibility infrastructure and fixes, route-level performance boundaries, code-splitting, image optimization, query-cache tuning, memoization, and bundle optimization. No new business functionality — every change here is presentation/infrastructure only (Architecture Review, 2026-08-12).
**Implemented in:** `packages/config/eslint/next.mjs`, `packages/ui/src/components/{dialog,skip-link,route-error,button,card,chat-bubble,feature-flag-card}.tsx`, every route segment's `loading.tsx`/`error.tsx` (both apps), `apps/web/src/app/{error,global-error,not-found,middleware}.tsx`, `apps/admin/src/app/{error,global-error,not-found}.tsx`, `apps/{web,admin}/next.config.ts`, `apps/web/src/features/crm/{lead-detail,pipeline-board}.tsx`, `apps/web/src/features/{workspace/branding-panel,settings/settings-home}.tsx`, `apps/admin/src/features/platform/{dashboard-view,break-glass-view,maintenance-view,feature-flags-view,governance-view}.tsx`

## Accessibility linting: a pre-existing gap this volume surfaced and fixed

`eslint-config-next` was listed as a devDependency in both apps but never actually spread into the active flat ESLint config — `packages/config/eslint/next.mjs` only ever imported the shared `baseConfig`, so every `jsx-a11y`/`react-hooks`/`@next/next` rule was dormant since this repo's inception, unrelated to this volume. Rather than pull in the whole `eslint-config-next` preset (which also carries React/Next rules with their own review surface), `eslint-plugin-jsx-a11y`'s own flat `recommended` config was added directly and scoped to what this volume actually needed. Activating it surfaced exactly 3 real issues across the whole repo, all fixed: `CardTitle`'s `<h3 {...props}>` pattern (content comes from spread `children`, which the rule can't see statically — documented `eslint-disable` with justification, not a real defect); `PlatformUserCard`'s test file passing a literal `role="PLATFORM_SUPER_ADMIN"` string (a business `PlatformRole` value colliding in name with the ARIA `role` attribute, not a real accessibility issue — same treatment); `Dialog`'s backdrop-click handler on a non-interactive `<dialog>` element (a documented, intentional convenience-only handler — Escape already provides the keyboard-equivalent dismissal per the WAI-ARIA APG modal pattern).

## Dialog: DS-001's Modal primitive, deferred since Volume-1, built on native `<dialog>`

`Dialog` (+ `DialogHeader`/`DialogTitle`/`DialogDescription`/`DialogFooter`) is built on the native HTML `<dialog>` element rather than a hand-rolled focus trap — the browser itself provides focus trapping, Escape-to-close (`cancel`→`close` events), and focus-return to the triggering element, all natively, with far less surface area for an accessibility-critical bug than reimplementing them. `showModal()`/`close()` calls are wrapped in `try/catch` so an engine without full `<dialog>` support degrades to an inert element rather than throwing (DS-001 §4.8's graceful-degradation policy). First real usage: Lead Detail's Convert-to-Customer confirmation (FRD-001 Volume-5), which had shipped without one specifically because this primitive didn't exist yet — that gap is now closed.

## Color contrast: two real WCAG AA failures found and fixed, one narrow gap documented

A computed WCAG relative-luminance audit (not eyeballed) against every token pairing found two real, material failures: white text on `bg-brand-500` (4.47:1, needs 4.5:1) and white text on `bg-danger-500` (3.76:1) — both used by every Primary and Destructive button in the app, plus `ChatBubble`'s outbound bubble, `SkipLink`'s focus pill, and both apps' `not-found.tsx` "Back to home" link. Fixed by moving one/two stops darker on their _existing_ scales (`brand-500`→`brand-600`, `danger-500`→`danger-700`) — no new color tokens invented, every combination now ≥6.29:1. A narrower, dark-mode-only shortfall was found and _not_ force-fixed: `Badge`'s `danger`/`info` variants at `-500/10` opacity tint measure 4.31–4.35:1 against a `neutral-900` background (just under 4.5:1) on 12px caption text — filed as Technical Debt rather than inventing a new intermediate color stop for a narrow, semantically-reinforced-by-text-label gap (badges never convey status by color alone). `neutral-400` placeholder text (2.56:1) was reviewed and left as-is — WCAG 1.4.3 doesn't require placeholder text to meet the same bar as real content, and it's used nowhere else.

## Route-level performance/error boundaries: every one of 59 route segments, not just the app root

Every route segment across both apps' `(workspace)`/`(platform)` route groups gained its own `loading.tsx` (generic 3-`SkeletonCard` fallback, deliberately uniform per §4.7's "no module-specific redesign") and `error.tsx` (scoped so an error in one screen doesn't take down the shared sidebar/header). The shared presentational body — `@wapp/ui`'s new `RouteError` — was extracted from `apps/web`'s pre-existing root `error.tsx` (whose own Volume-1 doc-comment had already anticipated this) so all ~63 error boundaries across both apps render identically and never surface a raw error message, only `error.digest` (TAD-001 ERR-002). `global-error.tsx` was added to both apps for the one case `error.tsx` can't reach — an error thrown in the root layout itself — rendering its own independent `<html>`/`<body>` with no dependency on `AppProviders` having mounted.

## Code-splitting: `next/dynamic` for every `recharts`-dependent view

The 5 screens importing `RevenueChart` (Billing/CRM Reports & Forecast in `apps/web`, Platform Analytics in `apps/admin`) now lazy-load their feature view via `next/dynamic`, code-splitting `recharts` — one of the heaviest dependencies in the app — out of those routes' main chunks. `experimental.optimizePackageImports: ["lucide-react", "recharts"]` was added to both `next.config.ts` files for per-icon/per-component tree-shaking on top of that. Pipeline's native-HTML5-drag-and-drop board was deliberately _not_ wrapped in `next/dynamic` — it carries no comparably heavy dependency (confirmed: no third-party DnD library, just `draggable`/`onDragOver`/`onDrop`), so there was nothing to code-split there.

## Memoization: one measured, justified target — not applied broadly

Memoization was essentially unused across the codebase before this volume (1 `useMemo`, 0 `useCallback`, 0 `React.memo` in either app's entire `src/`). Rather than apply it indiscriminately (itself a maintenance/performance anti-pattern), exactly one real, measured hot spot was fixed: `PipelineBoard`'s per-column `deals.filter()` — up to 200 deals × 6 columns, re-run on _every_ render, including the many `setDragOverColumn` updates `onDragOver` fires continuously during a single drag gesture. Grouped once via `useMemo` keyed only on `deals`, so drag-state changes no longer re-filter the whole list.

## Query cache tuning: per-family overrides where genuinely justified, not a blanket change

The global 30s `staleTime` (Volume-1) stays the default. Three Platform screens got a shorter, polling override matching Communication Inbox's own precedent (15s polling, Volume-4 — no WebSocket/SSE exists anywhere): Platform Dashboard (`systemHealth` is operator-relied-upon infra status), Break-Glass sessions (a multi-operator approval handoff), and Maintenance status (a platform-wide login gate — stale "operating normally" has amplified consequences). Two rarely-changed, Super-Admin-only config screens (Feature Flags, Governance Policies) got a _longer_ override (2 min) — both already invalidate their own query key immediately after every write, so a longer window never risks showing stale post-write data.

## `next/image`: both real `<img>` tags converted

The only two raw `<img>` tags in the repo (workspace logo previews in `branding-panel.tsx` and `settings-home.tsx`) now use `next/image` with `fill` + `sizes` (intrinsic dimensions are unknown — user-uploaded Cloudinary assets), both apps' `next.config.ts` already whitelisted the Cloudinary origin from Volume-3.

## A real bug this volume's own Lighthouse verification caught: `robots.txt`/`sitemap.xml`/`manifest.webmanifest`/`sw.js` were all being redirected to `/login`

`middleware.ts`'s matcher excluded `_next/static`, `_next/image`, `favicon.ico`, and image extensions — but not the four new infrastructure files this volume added. An unauthenticated request for any of them (exactly what a search crawler, a browser's manifest fetch, or a service-worker registration call all are) was silently redirected to `/login`, which meant: `robots.txt` served the login page's HTML instead of real directives (Lighthouse's `robots-txt` audit correctly flagged this as invalid), and the service worker registration threw `SecurityError: ... script resource is behind a redirect, which is disallowed` — a genuine, total PWA install/offline failure for any first-time visitor, not a theoretical one. Fixed in the middleware `matcher` regex alongside `favicon.ico`, since none of these are "pages" needing auth-gating. Caught only because Lighthouse was run for real against a real production build — a static/manual review would not have found it.

## Landmark completeness: `<main>` added to 6 places Lighthouse's `landmark-one-main` audit found missing

`(auth)/layout.tsx` (both apps), the offline fallback page, both apps' `not-found.tsx`, and — carefully, not universally — the four _root-level_ `error.tsx`/`global-error.tsx` call sites (wrapped at the call site, not inside `RouteError` itself, since `RouteError` is also reused by all ~59 _nested_ route error boundaries, which already sit inside their parent layout's own `<main>`; wrapping it there unconditionally would have created duplicate landmarks in the common case).

## Verified Lighthouse results (real production build, both apps)

Home page (`apps/web`, `/`): Accessibility 100, Best Practices 100, SEO 100, reproducibly, after the fixes above. Performance measured 75–88 across runs — bounded by Total Blocking Time, root-caused to `AppProviders`' full provider tree (Query/Theme/Auth/PWA/Toaster and their transitive dependencies) loading even for this placeholder page, which will be rebuilt entirely once the real Public Website module ships; filed as Technical Debt rather than premature-optimized for content that doesn't exist yet. This environment's own resource constraints (headless Chrome under sandboxed, memory-limited conditions after many consecutive verification runs) produced some non-reproducible outlier readings (`NO_LCP` trace failures, one transient `ChunkLoadError` that correctly triggered the new `global-error.tsx` boundary) — documented as measurement-environment noise, not application defects, since the underlying server and build artifacts were independently confirmed correct via direct `curl` checks each time.
