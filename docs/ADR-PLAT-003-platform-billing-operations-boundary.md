# Platform Billing Operations Boundary

**Status:** Accepted
**Date:** 2026-08-08
**Scope:** PRD-007 Volume-2 — Platform Billing Operations & Customer Support. How Platform Administration mutates real commercial state (Subscriptions/Invoices/Payments) it never owns, without duplicating any of Billing's own logic.
**Implemented in:** `apps/api/src/modules/platform/services/platform-subscriptions.service.ts`, `platform-invoices.service.ts`, `platform-payments.service.ts`, `platform-billing-dashboard.service.ts`; `apps/api/src/modules/billing/services/subscription.service.ts`, `invoice.service.ts`, `payment.service.ts`, `billing-history.service.ts` (all extended, not replaced); `apps/api/src/modules/billing/billing.module.ts` (widened `exports`)

## The decision: delegate through Services, not Repositories

Volume-1 (Workspace Registry) reached into `WorkspaceRepository` directly from Platform — a reasonable choice there, since Workspace's repository-level operations (`updateStatusWithReason`) carried nearly all the business logic themselves. Billing is different: `SubscriptionService`/`InvoiceService`/`PaymentService` hold real state-machine validation (eligible-status checks, duplicate-payment guards, invoice/payment relationship invariants) that a repository call alone would bypass. BR-006 ("Plan Change always delegates to Billing services") and §11 ("No duplicate invoice/payment/subscription logic") name this explicitly. `BillingModule.exports` was widened from `[UsageService, BillingReportsService]` to also include `SubscriptionService`, `InvoiceService`, `PaymentService`, and `BillingHistoryService` — Platform never imports a Billing repository directly.

## The id-resolution problem, and its one consistent solution

Every tenant-facing Billing method takes `workspaceId` (implicit from the caller's JWT). Every Platform route takes a bare entity id from the URL (`:id` = subscriptionId/invoiceId/paymentId — Platform Administration has no "current workspace"). Rather than have Platform reach into a repository to resolve one id into the other, each Billing service gained a small set of id-based entry points that resolve internally and then re-delegate to the exact same tenant-facing method:

```ts
async upgradeById(subscriptionId: string, planId: string, actorId: string) {
  const subscription = await this.findByIdOrThrow(subscriptionId);
  return this.upgrade(subscription.workspaceId, planId, actorId);   // same method tenants call
}
```

`getByIdForPlatform`/`upgradeById`/`downgradeById`/`cancelById` (Subscription), `getById`/`void` (Invoice — Invoice has no tenant-facing mutation to delegate through, so `void()` is new outright), `getById`/`refundById` (Payment) all follow this shape. No validation, event emission, or state transition is duplicated anywhere — the id-based method is purely a lookup plus a call to code that already existed.

## Two different kinds of Suspend

This volume's `PATCH /platform/subscriptions/:id/status` (targets `ACTIVE`/`SUSPENDED`/`CANCELLED`) is easy to confuse with Volume-1's `PATCH /platform/workspaces/:id/status` (targets `ACTIVE`/`SUSPENDED`/`ARCHIVED`) — both use the word "Suspend," on adjacent-looking routes, from the same module. They are not the same concept:

- **Volume-1's Workspace Suspend** (`PlatformWorkspaceRegistryService.suspend`) sets `WorkspaceStatus.SUSPENDED` directly — reserved for fraud/policy-violation/chargeback/abuse per that enum's own doc comment, and blocks login entirely via Identity's `WorkspaceStatusGateListener`.
- **This volume's Subscription Suspend** (`SubscriptionService.operatorSetStatus` → `operatorSuspend`) sets `SubscriptionStatus.SUSPENDED` and syncs `WorkspaceStatus.EXPIRED` — the exact same mapping the system's own non-payment suspend sweep (`suspendExpiredGracePeriods`) already uses (ADR-BILL-002). This is a billing-cause state (read-only, login still allowed) for a subscription an operator is manually managing (e.g., mid-dispute), never a fraud signal.

An operator-driven Suspend never writes `WorkspaceStatus.SUSPENDED` — only Volume-1's Workspace Registry does that. Getting this backwards would have meant a billing dispute silently blocking a tenant's login, which is not what any part of this document asked for.

`operatorActivate` (the `ACTIVE` target) covers both "Activate" (from `TRIAL`/`GRACE_PERIOD`) and "Resume" (from `SUSPENDED`) — the document names them as two actions, but they're mechanically identical (any non-`ACTIVE`, non-terminal status → `ACTIVE`, emit `SUBSCRIPTION_ACTIVATED`), so one DTO/status value covers both, matching Volume-1's own precedent (`WorkspaceStatus`'s single `PATCH .../status` endpoint covering three named actions with one field).

## `PLAN_CHANGED_BY_OPERATOR`: an audit signal, not a second Billing History entry

`upgrade()`/`downgrade()` already emit `SUBSCRIPTION_UPGRADED`/`DOWNGRADED`, already captured by `BillingHistoryListener`. When Platform calls `upgradeById`/`downgradeById`, that existing event still fires (with `actorId` = the operator's `platformUserId`) and is still the Billing History record of the change. `PLAN_CHANGED_BY_OPERATOR` is emitted separately, from `PlatformSubscriptionsService` (not from Billing) — a Platform-only signal that this particular change was operator-initiated, not tenant self-service. It deliberately has **no** `BillingHistoryListener` handler; adding one would double-record the same change. Billing's own `SubscriptionService` has no concept of "this actor is a platform operator" at all — it only ever receives an `actorId` string, exactly as it did before this volume.

## Security

`POST /platform/payments/manual` and `POST /platform/payments/:id/refund` reuse the same stricter 5-req/min throttle tier (SEC-009) already applied to the tenant equivalents and to Platform Auth (Architecture Review, 2026-08-08). Every Platform Billing controller follows the `@Public()` + `@UseGuards(PlatformAuthGuard, PlatformPermissionsGuard)` pattern established in ADR-PLAT-002 — complete isolation from tenant authentication, confirmed by this volume's own e2e suite (a tenant JWT against any `/platform/*` billing route fails at signature verification, the same result Volume-1's suite already established for non-billing routes).

## Permissions

Every money-touching permission (`MANAGE_SUBSCRIPTIONS`, `MANAGE_PAYMENTS`, `MANAGE_TRIALS`) is `PLATFORM_SUPER_ADMIN`-only. `VIEW_PLATFORM_BILLING` and `MANAGE_SUPPORT` are `FULL` for all three roles — a Support Manager/Executive can see everything and manage tickets, but cannot themselves extend a trial, change a plan, suspend a subscription, record a payment, or issue a refund (Architecture Review, 2026-08-08). §7 named no dedicated Invoice permission; `MANAGE_PAYMENTS` gates Invoice Void — Invoice and Payment are the same financial-document domain (`PaymentService` already writes `Invoice` state directly via `markPaidFromPayment`/`markRefunded`), and both candidate permissions resolve to Super-Admin-only anyway, so the choice has no practical access-control consequence.
