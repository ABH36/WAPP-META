# CRM Dashboard & Pipeline Strategy

**Status:** Accepted
**Date:** 2026-08-11
**Scope:** FRD-001 Volume-5 — CRM UI. How `apps/web` implements the Pipeline Kanban, Calendar, Reports, and Forecast screens, plus the permission-rendering rules that apply uniformly across every CRM screen built this volume.
**Implemented in:** `apps/web/src/features/crm/{pipeline-board,calendar-view,reports-view,forecast-view,dashboard-view}.tsx`, `apps/web/src/lib/{crm-transitions,calendar-range,permissions}.ts`, `apps/web/src/app/(workspace)/crm/{pipeline,calendar,reports,forecast}`

## Pipeline architecture: no dedicated endpoint — one broad Deal fetch, grouped client-side by stage

No `crm/pipeline`-shaped endpoint exists; `pipeline-board.tsx` calls the ordinary `dealService.list({page: 1, limit: 200})` (unfiltered by stage) once and groups the results into six columns client-side. This was chosen over six parallel per-stage `useQuery` calls because a Kanban board is conceptually one dataset viewed six ways, not six independent lists — one fetch avoids six separate loading/error states for what the user experiences as a single board. The 200-row limit is a pragmatic bound for a Kanban board's expected working set; if a workspace's active pipeline ever exceeds it, that's a real scaling question for a future volume, not silently handled here.

## Kanban composition: `PipelineColumn` + `DealTile`, drag-and-drop validated against the same transition table the Deal Detail page uses

The six columns are `OPEN, QUALIFICATION, PROPOSAL, NEGOTIATION, WON, LOST` — `OPEN` included as the first column per Architecture Review, correcting the original FRD's implied five-column list, since every Deal starts in `OPEN` and the backend never auto-transitions it. Dragging a tile only succeeds if `getValidDealTransitions(deal.stage)` includes the drop target — the same table `deal-detail.tsx`'s stage Select already uses — and a tile whose stage has no valid forward transitions (`WON`/`LOST`) simply isn't draggable at all (`draggable={canEdit && getValidDealTransitions(deal.stage).length > 0}`). Dropping onto Lost opens the same required-reason picker `deal-detail.tsx` uses before calling `updateStage(id, LOST, reason)` — the backend remains the actual enforcer of both the transition and the reason requirement; the board's own validation exists purely so an invalid drag never reaches the network as a doomed request.

## Forecast presentation: weighted pipeline forecast is never shown next to, or labeled like, the Dashboard's raw pipeline value

`ForecastReport.pipelineForecast` is probability-weighted (`value × probability/100`) — `forecast-view.tsx`'s `SummaryCard` explicitly captions it "Probability-weighted — distinct from the Dashboard's raw pipeline value" rather than letting the two numbers sit unlabeled next to each other where a reader might assume they're the same figure. Monthly/Quarterly/Yearly bucket selection is a client-side toggle over three arrays the single `forecast()` call already returns together — no separate request per period. No "probability breakdown" screen or field exists anywhere in the response; none was built (Architecture Review, 2026-08-11).

## Reports: Lead, Deal, and Activity only — export is a real authenticated binary download, not a link

Per the approved scope decision, only three of the FRD's named report types are backed by real endpoints (`GET /crm/reports/{leads,deals,activities}`) — "Sales Report" and "Customer Report" have no backend route and are filed as TD-032/TD-033 rather than built against guessed client-side aggregation. `reports-view.tsx` renders each report as a small `SummaryCard` grid plus one `RevenueChart` (bar or pie, whichever suits the report's own distribution field) and its own CSV/Excel export button. Export cannot be a plain `<a href>` — the endpoint requires the same Bearer token every other CRM call does, and the access token lives in memory only (`ADR-FE-001`) — so `crmService.exportReport()` fetches through the authenticated `apiClient` with `responseType: "blob"`, and `lib/download-blob.ts` triggers the actual browser save via a temporary object URL and hidden anchor click.

## Permission rendering: every CRM screen self-gates its own real read/write access — hide entirely, never a restricted placeholder

Consistent with the pattern established in FRD-001 Volume-4: every list and detail component in this volume checks its own real permission before rendering data, using `useHasPermission` (`!== NONE`) for reads and `useHasFullPermission` (`=== FULL`) for every write action (create/edit/archive/convert/assign/stage-transition/close) — the backend's `permissions.guard.ts` only ever checks `level !== NONE`, so a `VIEW_ONLY`/`TEAM_SCOPED`/`OWN_SCOPED` role isn't actually blocked server-side from calling a write route directly, only the frontend prevents it. A screen the viewer can't access renders an `Alert variant="info"` message and fires no request, rather than a 403-triggering call or a disabled-but-visible placeholder. Activities are the one exception to a single per-screen gate: because access is derived per-instance (AND-composed across `VIEW_CUSTOMERS`/`VIEW_DEALS` or `EDIT_CUSTOMER`/`CREATE_DEALS` when both refs are set), the standalone Activities list, the Calendar, and the Dashboard's Recent Activity all self-gate **per row** instead — a list may freely mix activities the viewer can and cannot see, and each row independently decides whether it renders at all. Sidebar navigation mirrors the same rule: `workspace-sidebar.tsx`'s `CRM_TABS` filters each item by its own `requires` permission (`null` for Activities/Calendar, matching their per-instance rather than per-screen gate), never a single all-or-nothing CRM section toggle.
