# Audit Strategy

**Status:** Accepted
**Date:** 2026-08-08
**Scope:** PRD-006 Volume-4 §4.1/§4.2/§4.3/§4.4/§4.5 — the canonical Audit Log pipeline, its relationship to a possible future platform-wide audit capability, Configuration History's value-chaining design, Data Export's reuse-not-rebuild posture, and Feature Flags' separation from Billing entitlements
**Implemented in:** `apps/api/src/modules/settings/listeners/audit-log.listener.ts`, `listeners/config-history.listener.ts`, `repositories/audit-log.repository.ts`, `repositories/config-history.repository.ts`, `queue/data-export.processor.ts`, `services/feature-flags.service.ts`

## Audit Logs are workspace-scoped and live in Settings now — not deferred to a future platform module

The only pre-existing code touching this area, `common/events/domain-event-logger.listener.ts`, is an explicitly temporary console logger whose own doc comment names a future **"Global Audit Center, per PRD-007"** as the real intended consumer. Resolved 2026-08-08, Architecture Review: that forward reference describes a _different, platform-wide, cross-tenant_ capability (PRD-007 is Platform Administration/Super Admin Console — WAPP's own internal team observing across every tenant), not this volume's workspace-scoped "who changed what in my workspace" audit trail. The same scope split already exists for Reports: `docs/ADR-CRM-021-crm-analytics-boundary.md` and `docs/ADR-BILL-010-billing-reporting-boundary.md` both explicitly separate workspace-scoped Reports (built) from a possible future platform-wide/cross-tenant Reporting capability (not built, not this volume's job). Audit Logs follow the identical pattern — this is genuinely new, workspace-scoped, and doesn't preclude a future platform-wide audit/ops center from also existing later.

`DomainEventLoggerListener` should be considered superseded for every event `AuditLogListener` now covers — it's dead weight once a real, persisted consumer exists for the same events, per its own doc comment's stated deletion condition ("once either of those modules subscribes for real"). Not removed in this pass to avoid touching an unrelated frozen file outside this volume's declared scope; flagged here for a future cleanup pass.

## Audit Logs cover a curated, representative event set — not literally every domain event

`AuditLogListener` subscribes to 20 of the ~70 domain events in the catalog: 4 Workspace (created/updated/team-invited/ownership-transferred), 4 CRM (customer-created/customer-blocked/lead-converted/deal-won), 2 Communication (whatsapp-connected/campaign-completed), 4 Billing (subscription-created/subscription-cancelled/invoice-paid/payment-failed), 1 Settings (settings-updated), 5 Integrations (integration-connected/disconnected, webhook-created, api-key-created/revoked). This mirrors the same "significant actions, not every mutation" posture Identity's own Login History already established for Authentication (records terminal login outcomes, not every intermediate auth-service call) — an audit trail exists to answer "what happened" for the events that matter to a workspace admin, not to be a full event-sourcing replica of the platform. Extending coverage to another event is purely additive (one more `@OnEvent` handler), never a redesign.

## AUTHENTICATION is composed at read time from Identity's LoginHistoryEntry, never re-persisted

§8's "no duplicate persistence of business entities" rule is applied literally here: Identity's `LoginHistoryEntry` (Volume-2) is already the persisted authentication audit trail. `AuditLogListener` has no Authentication handler at all; `AuditLogService.getAuditLogs(category=AUTHENTICATION)` instead calls `AuthService.getWorkspaceLoginHistory()` (new — resolves every workspace member's user id, then queries `LoginHistoryRepository.findByUsers()`) and maps the result into the same `AuditLogEntrySummary` shape the API already returns for every other category, so the distinction is invisible to a client. Mixing both sources into one paginated result was deliberately not attempted (merging two different collections' sort orders is real complexity for a first version) — a `category=AUTHENTICATION` query returns Identity's bounded recent-history results; every other category paginates `AuditLogEntry` normally.

## Configuration History's `previousValue` is chained, not diffed from the event payload

`WORKSPACE_UPDATED`/`SETTINGS_UPDATED` (Volumes 1-3) only ever carried a `section` marker, never the actual before/after values — modifying those already-frozen emit sites to carry a full diff was out of scope for this volume. Instead, `ConfigHistoryRepository.record()` reads the immediately preceding entry for the same `(workspaceId, area)` and uses its `newValue` as the new entry's `previousValue` (`null` on the very first change ever recorded for that area) — `newValue` itself is a live read of current state at the moment the triggering event fires. This produces a correct, self-consistent history chain without touching any frozen Workspace/Settings/Webhook write path. `WORKSPACE_UPDATED(section="business_profile")` is deliberately not tracked — §4.2's own area list names Business Hours and Notification Settings, not Business Profile.

## Data Export reuses CRM's/Billing's report generation; never rebuilds it

§11 ("Settings never owns CRM/Billing data") rules out Settings re-implementing row generation for Leads/Deals/Activities/Billing. `DataExportProcessor` calls `CrmModule`'s exported `ReportsService.exportReport()` and `BillingModule`'s exported `BillingReportsService.exportReport()` directly — the same CSV/Excel buffers those modules already produce for their own `/reports/export` endpoints, just wrapped in Settings' async job/queue/status infrastructure. Customers (no existing CRM export type) and Settings' own config (native to this module) are built directly in the processor, duplicating the already-established `toCsv`/`toExcelBuffer` pair a third time — consistent with this codebase's existing convention (CRM and Billing each already have their own copy; introducing a shared utility now would be a bigger deviation than following precedent). JSON is only supported for Customers/Settings — CRM's and Billing's export methods only ever produce CSV/Excel, so a JSON request against a CRM/Billing-backed entity type fails the job with a clear message rather than silently mis-formatting.

## Feature Flags are a different axis from Billing's PlanLimits entitlements

`PlanLimits` (Billing, Volume-3 of PRD-005) already has `crmEnabled`/`broadcastEnabled`/`campaignsEnabled`/etc. — per-_Plan_, commercial, static booleans (TD-014/015). §4.5's Feature Flags are per-_Workspace_, operational, admin-toggleable visibility switches — BR-005 ("Feature Flags never replace Billing entitlements") states the distinction explicitly in the source document itself, not something this ADR is inventing. `FeatureFlagKey` values (`CRM_MODULE`, `BILLING_MODULE`, `COMMUNICATION_MODULE`, `AI_ASSISTANT`, `BETA_FEATURES`) were deliberately named to avoid exact string collision with `PlanLimits`' field names, so the two concepts stay visually distinct in code and logs — a workspace toggling `CRM_MODULE` off changes UI visibility only; it never touches `PlanLimits.crmEnabled`, and nothing in either direction keeps them in sync.
