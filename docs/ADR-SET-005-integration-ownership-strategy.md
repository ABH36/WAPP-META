## Why App ID/App Secret/Webhook Verify Token were rejected

WAPP registers exactly one Meta App; every workspace connects its own WABA to that single app via Embedded Signup (`WhatsAppConnectionService.connect()`, Phase-4). This is what makes D004 (Tech Provider model — the customer owns their own Meta Business Account/WABA/phone number, WAPP never becomes a BSP reseller) work without WAPP holding customer WhatsApp credentials at the platform level. Letting a workspace configure its own App ID/App Secret would mean each workspace brings its own Meta App — a fundamentally different, unapproved architecture, not a Settings field. `META_APP_ID`/`META_APP_SECRET`/`META_WEBHOOK_VERIFY_TOKEN` stay exactly where they already were: `apps/api/src/config/configuration.ts`, read once by `MetaApiClient`, never touched by this volume.

## Why Email stops at configuration

§4.2's own line — "No email sending logic belongs here" — combined with BR-001 ("Settings owns configuration only. Business execution belongs to the owning bounded context") means Settings' job ends at storing a validated provider config. `infrastructure/email/` (Resend-based, global, used by every transactional email in the platform today) is untouched. `EmailIntegrationService.testConnection()` performs a real SMTP handshake (`nodemailer`'s `transporter.verify()`) against the saved config — genuine validation (BR-005), not a stub — but no email is ever sent through it. Wiring a workspace's own configured provider into the actual send pipeline is a separate, larger initiative (replacing a global sender with per-workspace provider selection touches every module that sends email, not just Settings) and was deliberately not attempted this volume.

## Why API Keys split like OAuth

§3 states plainly: "Identity Owns: API authentication." §4.5 (OAuth) independently arrives at the same split for connection metadata vs. credential handling — "Settings never stores refresh tokens directly. Identity owns secure credential handling." API Keys get the identical treatment: the `ApiKey` collection (name, prefix, scope, status, timestamps, and the bcrypt `keyHash`) lives in Identity — `apps/api/src/modules/identity/schemas/api-key.schema.ts` — because validating a presented key _is_ authentication, the same reasoning already covering passwords (`PasswordService`) and sessions. `SettingsApiKeysService` is a thin proxy over Identity's `ApiKeyService`, the exact shape `docs/ADR-SET-004-identity-orchestration-strategy.md` already established for `SecuritySettingsService` → `AuthService`. Keys are bcrypt-hashed, never `TokenEncryptionService`-encrypted — a key, like a password, is only ever verified, never read back. `ApiKeyGuard` was built (mirrors `JwtAuthGuard`'s shape) but is not registered as a global guard or applied to any route: no protected Developer API surface exists yet to consume it (§4.4/§12 name "Developer Settings" as future scope). It exists so a generated key is a genuinely verifiable credential today, ready to wire onto a route the moment one exists.

## Webhook secrets follow the same one-time-display posture as API Keys

§4.3 gives Webhooks a `secret` field with no explicit "shown once" rule the way §4.4/BR-007 states for API Keys — but the reasoning is identical (BR-002: credentials never returned through public APIs) and the secret serves the same purpose as any other bearer credential (HMAC-signing outbound deliveries so the receiving endpoint can verify authenticity). `WebhookService.create()` returns the raw secret exactly once, in the creation response, and `WebhookConfig.secretEncrypted` is `select: false` everywhere else — applying BR-002/BR-007's already-approved pattern consistently to a second secret type, not inventing a new rule.
