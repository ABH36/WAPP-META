# TAD-001 v1.2 — Security Standards Restoration Patch

**Applies to:** TAD-001 v1.1, Section 18 (Security Standards)
**Status:** Final Review
**Reason:** Restores standards mandated in the original Engineering Standards document (project's foundational constitution) that were never carried into TAD-001's actual Security Standards section. No new architecture introduced — this restores an already-approved baseline.

---

## Update Section 18 — Security Standards

Existing SEC-001 through SEC-007 remain unchanged. Add the following:

### SEC-008 — Helmet

All HTTP responses shall set secure headers via Helmet (or NestJS's built-in equivalent) at the application-bootstrap level, applied globally — not opt-in per route.

Mandatory headers include: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` (see SEC-011), `Strict-Transport-Security` (HSTS, min 1 year, `includeSubDomains`), `Referrer-Policy: strict-origin-when-cross-origin`.

### SEC-009 — Rate Limiting

Every API endpoint is rate-limited by default. No endpoint is exempt without explicit architectural justification recorded against this document.

| Tier                                                        | Limit                                         | Applies to                                                                    |
| ----------------------------------------------------------- | --------------------------------------------- | ----------------------------------------------------------------------------- |
| Authentication endpoints (login, register, forgot-password) | 5 requests / minute / IP                      | Brute-force and account-enumeration protection                                |
| General authenticated API                                   | 300 requests / minute / user                  | Normal application usage                                                      |
| Webhook ingestion (Meta)                                    | Not rate-limited by WAPP (Meta is the caller) | Idempotency (already established) is the correct control here, not throttling |
| Public website forms (Contact, Newsletter)                  | 10 requests / hour / IP                       | Spam prevention                                                               |

Rate-limit violations return HTTP 429 with the standard error envelope (TAD-001 API-002) and never expose the underlying limiting mechanism.

### SEC-010 — CORS

Cross-Origin Resource Sharing is explicitly allow-listed, never wildcarded (`*`) in production.

Allowed origins: the Public Website domain, the Workspace App domain, and the Platform Administration domain (per SDP-001's separate-app decision) — each explicitly enumerated per environment (dev/staging/production). Credentials (cookies, Authorization headers) are only permitted for allow-listed origins.

### SEC-011 — Clickjacking Protection

`X-Frame-Options: DENY` and the `frame-ancestors 'none'` CSP directive (SEC-013) are mandatory on every response. No WAPP page may be embedded in an `<iframe>` by a third party. This is unconditional — there is no approved embedding use case in Phase-1 (no White Label, per D010/AHD-001 Out of Scope).

### SEC-012 — CSRF Protection

Since AUTH-001 (TAD-001) uses JWT Bearer tokens for API authorization rather than cookie-based sessions, CSRF risk is substantially reduced for the API itself. However:

- Any endpoint that _does_ rely on cookies (e.g., the Refresh Token, per AUTH-003, if stored as an HttpOnly cookie) shall use the `SameSite=Strict` cookie attribute as the primary CSRF defense.
- State-changing public-website forms (Contact, Newsletter) that don't carry a JWT shall use a CSRF token (double-submit cookie pattern) since they're unauthenticated.

### SEC-013 — Content Security Policy (CSP)

A strict CSP is mandatory in production:

```
default-src 'self';
script-src 'self' 'strict-dynamic';
style-src 'self' 'unsafe-inline'; // required for Tailwind's runtime style injection during dev; production build should minimize this
img-src 'self' data: https://res.cloudinary.com;
connect-src 'self' https://graph.facebook.com; // Meta Cloud API
frame-ancestors 'none'; // see SEC-011
```

CSP is reported, not just enforced — violations post to a logging endpoint (`report-uri` / `report-to`) so misconfigurations are caught during QA rather than silently breaking a feature in production.

### SEC-014 — XSS Protection

- **Output encoding is mandatory** for all user-generated content rendered in the UI (Customer names, Note content, Broadcast message previews) — React's default JSX escaping covers most cases; any use of `dangerouslySetInnerHTML` requires explicit sanitization (DOMPurify) and architectural sign-off, logged as an exception.
- **Input validation** (already required by API-005 / DTOs) is the first line of defense; CSP (SEC-013) and output encoding are defense-in-depth, not substitutes for it.
- WhatsApp message content specifically: since messages are rendered from external (customer) input, message bodies are treated as plain text only in the UI — no HTML rendering of inbound message content, ever.

### SEC-015 — Output Sanitization

Every API response is checked against TAD-001 ERR-002 (no stack traces / internal paths / secrets) as a blocking CI check, not just a code-review convention — a response-shape linter or integration test asserts this for at least the authentication and error-handling paths.

### SEC-016 — Request Size Limits

- JSON body size: 1MB default, per-endpoint override only where justified (e.g., none currently — file uploads go through Cloudinary's direct-upload flow, not through the NestJS body parser, specifically to avoid needing a larger limit here).
- File upload size: enforced at the Cloudinary/upload-widget layer per PRD's stated file-type/size validation requirement (Engineering Standards, "File Storage" section) — not re-litigated here, just confirmed as still binding.

---

## Consistency Statement

This patch adds no new technology, no new architectural component, and modifies no approved business rule. It restores six standards (Helmet, Rate Limiting, CORS, Clickjacking, CSP, XSS/Output Sanitization/Request Size) that were mandated in the project's original Engineering Standards document and inadvertently dropped when TAD-001 was first drafted. SEC-001 through SEC-007 are unchanged and remain fully in force.
