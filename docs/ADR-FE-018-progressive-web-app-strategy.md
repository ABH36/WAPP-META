# Progressive Web App Strategy

**Status:** Accepted
**Date:** 2026-08-12
**Scope:** FRD-001 Volume-9 — PWA scope is `apps/web` only (Architecture Review, 2026-08-12: "apps/admin remains a standard authenticated administration console. No service worker, manifest or install experience shall be added to apps/admin."). Covers the Web App Manifest, service worker, offline shell, install prompt, and update-notification flow.
**Implemented in:** `apps/web/src/app/{manifest.ts,sw.ts,layout.tsx,offline/page.tsx,robots.ts,sitemap.ts}`, `apps/web/src/{components/pwa-manager.tsx,lib/use-online-status.ts,components/layout/workspace-header.tsx,middleware.ts}`, `apps/web/next.config.ts`, `apps/web/public/icons/`, `pnpm-workspace.yaml`

## Manifest and icons: real, functioning, explicitly placeholder-marked

`app/manifest.ts` (Next's typed App Router convention, not a static JSON file) declares `name`/`short_name`/`start_url: "/dashboard"`/`display: "standalone"`/`theme_color`/`background_color` and three icon entries (192, 512, and a 512 maskable variant). No real WAPP logo/brand asset exists anywhere in this repo yet, so the icons are a deliberate, minimal placeholder: a solid `brand-600` square with a centered white circle, generated via a ~60-line pure-Node PNG encoder (no image-generation dependency needed for a flat-color-plus-circle raster) rather than left blank or faked as a "real" logo. `layout.tsx` additionally sets `viewport.themeColor` (light/dark pair) and `metadata.appleWebApp` (iOS's separate Add-to-Home-Screen mechanism, since iOS Safari doesn't read the Web App Manifest's `display`/`name`).

## Service worker: Serwist, an explicit allow-list of runtime caching, never `defaultCache`

`serwist`/`@serwist/next` were installed — the first PWA/service-worker library in this repo. `sw.ts` deliberately does **not** use Serwist's generic `defaultCache` preset (which includes a broad same-origin "others" `NetworkFirst` bucket, among other rules) — instead, `runtimeCaching` is a hand-written, minimal, 3-rule allow-list: `CacheFirst` for `/_next/static/*` (immutable, content-hashed) and same-origin images/fonts, and `NetworkFirst` (5s timeout) for navigation requests only, falling back to the precached `/offline` shell. `precacheEntries` (Serwist's build-time manifest of the Next.js static output) and those 3 rules are the _entire_ caching surface. This directly implements the Architecture Review's explicit constraint: **"Offline mode may cache only static assets and application shell. Authenticated API responses shall never be cached."** Every request to `NEXT_PUBLIC_API_URL` is a different origin/port from this app (confirmed via `apps/web/.env.example`) and matches none of the 3 rules — it is never touched by the service worker, cached or not, identical to behavior with no service worker at all. The build-time-only flag `disable: process.env.NODE_ENV === "development"` keeps `/sw.js` from existing at all in dev, matching how every PWA tooling guide recommends avoiding service-worker interference with HMR.

## A real performance regression this volume's own Lighthouse verification caught and fixed

`PwaManager` initially called `navigator.serviceWorker.register()` inside a `useEffect` with no deferral — registering, installing, and precaching immediately on mount, competing with initial hydration for the main thread. A production Lighthouse run measured this adding roughly 700ms of Total Blocking Time (480ms → 1180ms) once the registration was actually succeeding (see below). Fixed by deferring registration until the window `load` event — the standard, widely-documented service-worker-registration performance practice — which brought TBT back to its original range. This was caught only because Lighthouse was run against a genuinely working registration; a synthetic/mocked check would not have surfaced it.

## A real, more serious bug the same verification pass caught: PWA install/offline was completely broken behind a redirect

`middleware.ts`'s route matcher did not exclude `manifest.webmanifest` or `sw.js` (see ADR-FE-017's fuller account — the same gap also broke `robots.txt`/`sitemap.xml`). Every unauthenticated request for either file was silently redirected to `/login`, and browsers correctly refuse to register a service worker whose script response is a redirect (`SecurityError: ... behind a redirect, which is disallowed`) — meaning the entire PWA install and offline experience was non-functional for any first-time or logged-out visitor before this fix. Fixed in the middleware `matcher` regex.

## Install prompt and update notification: the existing `Toaster`, not a new banner primitive

`PwaManager` is a single headless client component (returns `null`) mounted once from `AppProviders`. It listens for `beforeinstallprompt` (calls `preventDefault()`, stores the event, shows a persistent `sonner` toast with an "Install" action that calls the captured event's `.prompt()`) and for a waiting/updated service worker (shows a persistent "Reload" toast that posts `SKIP_WAITING` to the waiting worker, then reloads on `controllerchange`). Reusing the existing global `Toaster` (`AppProviders`, `sonner`) with `duration: Infinity` + an action button gives the same persistent, dismissible, actionable UI a dedicated banner component would, with zero new `packages/ui` surface — consistent with this engagement's "don't build near-duplicate primitives" discipline. `skipWaiting: false`/`clientsClaim: true` in `sw.ts` make this an explicit, user-initiated update flow rather than silent auto-activation (§4.3/§11's "Update flow"/"Update notification" requirements).

## Offline detection and fallback: read-only, matching BR-005 literally

`use-online-status.ts` (a new pure-logic hook, unit-tested) tracks `navigator.onLine` plus the `online`/`offline` window events; `workspace-header.tsx` renders a small "Offline" `Badge` when it's `false`. `app/offline/page.tsx` is the service worker's navigation fallback (`sw.ts`'s `fallbacks.entries`) — a plain retry UI (`window.location.reload()`), no data fetching, no mutation capability of any kind, matching BR-005 ("offline mode never performs mutations") by construction rather than by convention. `/offline` was added to `middleware.ts`'s `PUBLIC_PATHS` for a specific reason: the service worker precaches this page's _real_ content the first time any browser (signed in or not) visits while online — if it were gated like every other route, an unauthenticated device would precache the `/login` redirect instead of the actual offline page.

## A real pnpm dependency-resolution collision, found and fixed correctly (not worked around)

Installing `serwist` introduced `zod@4` as a private, correctly-isolated dependency of `@serwist/build`/`@serwist/next`/`@serwist/webpack-plugin`. `@hookform/resolvers` (used by every `zodResolver()` call site in `apps/web`, all built against zod v3) declares no `zod` dependency of its own — it relies entirely on pnpm's shared virtual-store fallback slot for undeclared/phantom imports, which started resolving to the newly-present v4 once both versions existed in the store, producing a real `ZodType` shape mismatch (`$ZodTypeInternals`, a v4-only type) across 6 files. A blanket `pnpm.overrides: {zod: "^3.23.8"}` was tried first and correctly rejected after verification — it force-downgrades `@serwist/build`'s own explicit `"zod": "4.4.3"` pin too, breaking it at runtime (`schema.implementAsync is not a function`, confirmed via a real `next build`). The correct fix, applied in `pnpm-workspace.yaml`'s `packageExtensions`, patches `@hookform/resolvers`'s own manifest to declare the zod v3 dependency it always actually needed — giving it a private, correctly isolated instance with zero effect on `@serwist/build`'s independent v4 resolution. Verified via a full `next build` succeeding cleanly after the fix (Serwist's own service-worker bundling step completing without error).
