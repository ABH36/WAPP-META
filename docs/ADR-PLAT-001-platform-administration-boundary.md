# Platform Administration Boundary

**Status:** Accepted
**Date:** 2026-08-08
**Scope:** PRD-007 Volume-1 — Platform Administration & Tenant Management. The first platform-scoped (cross-tenant), not workspace-scoped, bounded context in this codebase, and the architectural rules that keep it from leaking into or being leaked into by every tenant module.
**Implemented in:** `apps/api/src/modules/platform/` (all of it), plus targeted extensions to Workspace, Identity, Settings, CRM, Communication, Billing (see "What every other module gained" below)

## Why this needed its own ADR

Every module built before this one is workspace-scoped: every query carries a `workspaceId`, every permission check resolves against one tenant's `TenantRole`, and the one-directional dependency graph (Identity → Workspace/Communication/CRM/Billing → Settings) has never had a module positioned to legitimately read across every workspace at once. Platform Administration is exactly that module. Left unconstrained, "read across every workspace" is exactly the kind of capability that invites either a security hole (an ordinary tenant Owner reaching Platform data) or an architecture violation (Platform's own convenience creating a reverse dependency edge into a module that must never depend on it). This ADR fixes both.

## Dependency direction: Platform is the new most-downstream module

Platform imports `WorkspaceModule`, `IdentityModule`, `CrmModule`, `CommunicationModule`, `BillingModule`, and `HealthModule` — for the Dashboard's cross-tenant aggregate reads and the Registry's Workspace writes. Nothing imports `PlatformModule`. This is a strict extension of the existing graph, not a new shape: Platform simply sits one layer further downstream than Settings did. The one place this direction would have been violated — Identity's `AuthService.login()` needing to react to a Platform-owned Suspend/Archive/Maintenance action — is solved the same way ADR-SET-008 already solved an identical problem for Settings' Maintenance Mode: events out, a small local read model in, never a reverse import. See "Event-driven decoupling, extended twice" below.

## Cross-tenant reads are new; they're deliberately narrow

Before this volume, every read in the entire application was workspace-scoped except `Plan` (a small, genuinely global reference catalog — not an aggregate over tenant data). Two genuinely new cross-tenant read paths were added, and each was scoped as narrowly as the approved document allowed:

- **Platform Dashboard (§4.2)** aggregates live at read time — `Workspace.countAll()`/`countByStatus()`, `UserRepository.countAll()`, `LeadRepository.countAll()`, `DealRepository.countAll()`, `MessageRepository.countAll()`, and `BillingReportsService.getPlatformRevenueTotal()` — mirroring the existing CRM/Billing **Reports** pattern (compute on demand, persist nothing) rather than the Billing **Usage-counter** pattern (event-driven running totals). Dashboard metrics are current-state snapshots, not historical counts, so there is nothing to keep incrementally in sync.
- **Workspace Search (§4.6)** is limited to Workspace (by name) and User (by name/email) only, per the Architecture Review's resolution to Question 3. Customer/Lead/Invoice cross-tenant search was explicitly deferred — those are real customer PII living inside tenant boundaries, and searching across them needed its own scoping decision, not an incidental extension of this volume's search box. `UserRepository.searchAcrossWorkspaces()` and `WorkspaceRepository.listAllForPlatform()` are the only two cross-tenant query methods this volume added; no other repository gained a similar method.

Every cross-tenant read is mapped through a flattened summary type (`PlatformWorkspaceSummary`, `PlatformSearchUserSummary`) before it reaches a controller response — the same "one place a Document is flattened into what a client is allowed to see" convention already established by `toWorkspaceProfile`/`toUserProfile` (`apps/api/src/modules/workspace/mappers/workspace.mapper.ts`, `apps/api/src/modules/identity/mappers/user.mapper.ts`). A raw Mongoose document is never returned directly from a Platform controller — `passwordHash` and other internal fields never reach the wire this way.

## `WorkspaceStatus.ARCHIVED`: a new terminal status, independent of the CANCELLED retention flow

The document's Archive action needed a status to write. Two options existed: reuse the existing `CANCELLED` → 90-day-retention flow (ADR-020), or add a new value. Resolved via the Architecture Review (Question 4): Archive is a platform-admin-only action to remove a workspace (test/spam/abandoned) from the active registry — semantically nothing like a customer's subscription lapsing. `WorkspaceStatus` gained a sixth value, `ARCHIVED`, added to `LOGIN_BLOCKED_WORKSPACE_STATUSES` alongside `SUSPENDED` (both block login harder than `EXPIRED`'s read-only gate), and is never auto-derived from or into the `CANCELLED` flow. `Workspace` also gained `statusReason`/`statusChangedAt`/`statusChangedBy` — populated only by a Platform Administrator's Suspend/Reactivate/Archive action, left `null` for every billing-lifecycle-driven transition, since those have nothing to attribute a reason to.

## Event-driven decoupling, extended twice more

ADR-SET-008 established the pattern once (Settings' Maintenance Mode → Identity's local read model). This volume needed it twice more, for the same reason each time: a downstream/upstream module reacting to a Platform-owned state change without Platform being importable by the module that needs to react.

1. **Workspace Suspend/Reactivate/Archive → Identity's login gate.** `WORKSPACE_SUSPENDED`/`WORKSPACE_REACTIVATED`/`WORKSPACE_ARCHIVED` are emitted by `PlatformWorkspaceRegistryService`; Identity's new `WorkspaceStatusGateListener` keeps the existing `WorkspaceMaintenanceState` collection's new `loginBlocked` field in sync (the same collection Volume-4's Maintenance Mode already uses, extended with a second independent flag rather than a second collection — both flags gate the same thing, a new login attempt, so one lookup answers both questions). `AuthService.login()` checks `isLoginBlocked` before the pre-existing `isMaintenanceMode` check, using `ForbiddenException` (403) — harder than Maintenance Mode's `ServiceUnavailableException` (503), matching the "Suspended is harder than Maintenance" semantics from `WorkspaceStatus`'s own doc comment.
2. **Platform Feature Flag overrides → Settings' Feature Flags read.** `PLATFORM_FEATURE_UPDATED` is emitted by `PlatformFeatureFlagsService`; Settings' new `PlatformFeatureOverrideListener` keeps a new local read model (`PlatformFeatureOverrideState`, one document per `FeatureFlagKey`) in sync. `FeatureFlagsService.list()` now resolves in three tiers — platform override (if present) → workspace's own toggle → hardcoded default — with the override always winning when set, but never destroying the workspace's underlying stored value (clearing the override lets the workspace's own choice take effect again immediately, no re-toggle required).
3. **Platform-wide Maintenance → Identity's login gate (a second, independent flag).** `PLATFORM_MAINTENANCE_ENABLED`/`DISABLED` are emitted by `PlatformMaintenanceService`; Identity's new `PlatformMaintenanceGateListener` keeps a brand-new singleton collection, `PlatformMaintenanceGate` (a `{key: "singleton", enabled}` document — genuinely no `workspaceId`, unlike every other read model in Identity), in sync. `AuthService.login()` checks this gate first, before any per-workspace check, since a platform-wide outage applies regardless of which workspace a user belongs to — checked even for a user with no workspace yet (`workspaceId === null`), unlike the per-workspace checks, which skip entirely in that case.

In every case, `EventEmitter2` is already `@Global()`, so no new module-import edge is introduced in either direction — consumers subscribe via `@OnEvent`, never by injecting a Platform service.

## Confirmed out of scope (do not build without a new approval)

Per the Architecture Review's explicit confirmation: Trial Extension, Subscription/Plan Administration, Payment/Refund Operations, Billing Administration, Break-Glass Access, Global Audit Center, Support Sessions, and cross-tenant CRM/Billing search. Break-Glass Access and Support Sessions are tracked as `docs/TECH-DEBT.md` TD-021 (Cross-Tenant Support Access) rather than silently dropped, since they're a real, named future need — just not this volume's.
