# Global Audit Center Strategy

**Status:** Accepted
**Date:** 2026-08-10
**Scope:** PRD-007 Volume-3 §4.6/§4.7 — Global Audit Center & Investigation Timeline. How platform-wide events get a durable audit trail without duplicating storage that already exists elsewhere in the system.
**Implemented in:** `apps/api/src/modules/platform/schemas/platform-audit-entry.schema.ts`, `repositories/platform-audit.repository.ts`, `services/platform-audit.service.ts`, `listeners/platform-audit.listener.ts`, `services/platform-investigation.service.ts`, `controllers/platform-audit.controller.ts`, `platform-investigation.controller.ts`

## Hybrid, not "one new collection for everything"

§4.6 describes the Global Audit Center as covering Workspace Suspension, Billing Actions, Support Sessions, and Platform Configuration changes as if they were one uniform stream. They are not uniform in this codebase: three of those four already have a durable, authoritative home — Workspace Suspension writes to Settings' `AuditLogEntry` (via `AuditLogService`, workspace-scoped), Platform Billing Actions write to `BillingHistoryEntry` (`BillingHistoryService`), and neither needed a second, parallel copy. Only Support Session lifecycle (Break-Glass request/approve/start/end/expire, this volume's own new concept) and a real, previously-unaudited gap in Volume-1 — `PLATFORM_FEATURE_UPDATED`, `PLATFORM_MAINTENANCE_ENABLED`/`DISABLED` — had nowhere to persist to at all.

The resolution: a genuinely new `PlatformAuditEntry` collection (`platform_audit_entries`) persists only the events with no other durable home. Everything else is composed at read time from its existing owner. This was resolved as a hybrid specifically because the alternative — one new collection duplicating Billing History and Settings' Audit Log — would mean two sources of truth for the same fact (a voided Invoice would exist in both `BillingHistoryEntry` and a new `PlatformAuditEntry`, with no mechanism keeping them consistent if either is ever queried or corrected independently), a problem this codebase has consistently avoided (Volume-2's `PLAN_CHANGED_BY_OPERATOR` is emitted precisely _without_ a `BillingHistoryListener` handler, for the same reason — see ADR-PLAT-003).

| Event source                                                                         | Persisted into `PlatformAuditEntry`?                                              | Actual source of truth                                                                                 |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `BREAK_GLASS_REQUESTED`/`APPROVED`, `SUPPORT_SESSION_STARTED`/`TERMINATED`/`EXPIRED` | **Yes** — no other collection tracks Support Session lifecycle                    | `PlatformAuditEntry` (new this volume)                                                                 |
| `PLATFORM_FEATURE_UPDATED`, `PLATFORM_MAINTENANCE_ENABLED`/`DISABLED`                | **Yes** — real Volume-1 gap, these events fired but nothing durable ever listened | `PlatformAuditEntry` (new this volume); `workspaceId` always `null` (platform-wide, not tenant-scoped) |
| Workspace Suspension/Activation/Archival                                             | No                                                                                | `AuditLogEntry` (Settings, existing)                                                                   |
| Platform Billing Actions (Trial Extend, Plan Change, Void, Refund, Verify)           | No                                                                                | `BillingHistoryEntry` (Billing, existing)                                                              |

## `DomainEventLoggerListener` was ruled out as a foundation

Before settling on a new collection, a background research pass checked whether an existing generic listener could be extended instead. `DomainEventLoggerListener` (pre-existing) turned out to be structurally unsuited: it logs every domain event to the application's structured logger (Pino) for operational/debugging visibility, not to a queryable, durable store — there is no collection behind it, no query surface, and no retention guarantee beyond whatever the log pipeline itself keeps. Treating it as a foundation would have meant either bolting persistence onto a component whose entire purpose is ephemeral operational logging, or silently changing its behavior for every existing event it already handles. `PlatformAuditListener` is a new, separate `@OnEvent` listener with its own 8 handlers — `DomainEventLoggerListener` is untouched and continues logging in parallel, exactly as it did before this volume.

## What each listener handler does

`PlatformAuditListener` has 8 `@OnEvent` handlers. The 5 Support/Break-Glass handlers (`BREAK_GLASS_REQUESTED`, `BREAK_GLASS_APPROVED`, `SUPPORT_SESSION_STARTED`, `SUPPORT_SESSION_TERMINATED`, `SUPPORT_SESSION_EXPIRED`) share one private `record()` helper, since all 5 payloads carry the same shape (`workspaceId`, `actorId`, plus event-specific `metadata`). The 3 platform-wide handlers (`PLATFORM_FEATURE_UPDATED`, `PLATFORM_MAINTENANCE_ENABLED`, `PLATFORM_MAINTENANCE_DISABLED`) are written as 3 separate explicit handlers rather than folded into the shared helper, because their payloads have no `workspaceId` at all (`PlatformAuditEntry.workspaceId` is `null` for all three) — merging them into the generic helper would have meant the helper silently accepting an optional field it doesn't actually need for 5 of its 8 callers, the kind of implicit-by-omission ambiguity this codebase has avoided elsewhere (e.g., ADR-PLAT-003's explicit choice not to have `PLAN_CHANGED_BY_OPERATOR` reuse `BillingHistoryListener`'s handler).

## Investigation Timeline: a normalized read-time projection, not cross-source pagination

`PlatformInvestigationService.getTimeline(workspaceId, limit)` merges 4 heterogeneous sources — `PlatformAuditEntry`, `AuditLogEntry`, `BillingHistoryEntry`, `LoginHistoryEntry` — into one `InvestigationTimelineEntry[]` shape (a common `occurredAt`/`eventType`/`description`/`actorId`/`metadata` projection each source's own repository already exposes a `findByWorkspace`/`listRecentForWorkspace`-shaped method for). The implementation fetches the top-`N` most recent entries per source, normalizes them into the common shape, merges, sorts descending by `occurredAt`, and slices to `limit` client-side (in `PlatformInvestigationService`, not in any repository).

This is deliberately simple, not true cursor-based pagination across 4 independent collections. A cursor that stays consistent across 4 sources with different write cadences and no shared sequence number would need either a merged/materialized view (a real, standing infrastructure investment §4.7 doesn't ask for) or a composite cursor encoding a position in each of the 4 sources independently (meaningfully more complexity for a feature whose stated purpose — per §4.7 — is giving a Support agent a fast, readable timeline while investigating a specific issue, not exhaustively paging through a tenant's entire history). This limitation was accepted for now on the same precedent TD-020 (Audit Storage Strategy) already established for Settings' own `AuditLogEntry` — pagination-at-scale for audit-shaped data is a deferred, explicitly tracked concern, not a gap unique to this feature. If a real need for deep cross-source paging emerges, it's new scope, not a retrofit.

## Security

Every route under `/platform/audit/*` and `/platform/investigation` requires `VIEW_GLOBAL_AUDIT`/`VIEW_INVESTIGATION` respectively — both `FULL` for all three platform roles per the Architect's approved table, on the reasoning that audit visibility itself is not a privileged write capability the way approving/starting a Support Session is; restricting _who can see the audit trail_ more tightly than _who can act_ would be backwards. `GET /platform/investigation` additionally sits behind `SupportSessionGuard` (an active Support Session for the target `workspaceId` is required) — consistent with the Workspace Overview's own gating in ADR-PLAT-005, since an investigation timeline is tenant-specific data the same way the overview is.
