# Performance & Scalability Strategy

**Status:** Accepted
**Date:** 2026-08-17
**Scope:** PHD-001 Volume-3 (Performance, Scalability & Production Infrastructure) — the application-level half of the volume: BullMQ per-queue tuning, MongoDB connection pool configuration, Redis-backed rate limiting (correctness and its own newly-discovered limits), request body-size limits, frontend bundle-budget tooling, and the evidence-driven resource-limit adjustment that came out of k6 load testing. See `docs/ADR-PHD-006-production-infrastructure-strategy.md` for the Docker/deployment-topology half of the same volume.
**Implemented in:** `apps/api/src/{main.ts,app.module.ts,config/{configuration,env.validation}.ts,database/database.module.ts,infrastructure/redis/{redis.module,redis-throttler-storage.service}.ts}`, 11 BullMQ processor files under `apps/api/src/modules/*/queue/` and `apps/api/src/infrastructure/email/`, `apps/web/src/features/communication/*.tsx`, `apps/{web,admin}/next.config.ts`, `docker-compose.prod.yml`, `k6/`

## The core discipline this volume was built around: measure before tuning, tune before guessing

Every numeric default introduced this volume — BullMQ concurrency per queue, Mongo pool size, the API container's CPU allocation — is either a conservative, explicitly-documented-as-provisional starting value, or a value that was subsequently revised because k6 load testing produced concrete evidence it needed to change. Nothing here was tuned by intuition alone; where intuition and measurement disagreed (the API CPU limit, see below), measurement won.

## BullMQ: per-queue concurrency, retry policy, and job retention — not one-size-fits-all

Before this volume, all 11 BullMQ queues ran on `@nestjs/bullmq`'s defaults: unset concurrency (effectively 1), no `defaultJobOptions`, no `attempts`/`backoff` on most `queue.add()` call sites. Each queue now gets a concurrency value sized to its actual job shape, not a single platform-wide constant:

- **High-throughput, short-lived jobs** (`email`: 5, `webhook-delivery`: 5) — many small, independent, network-bound jobs where parallelism directly reduces backlog drain time.
- **Moderate-throughput** (`broadcast-execution`: 3) — bounded by Meta Graph API's own per-connection rate limits more than by this platform's own capacity, so concurrency is set to avoid tripping Meta's limits rather than to maximize local throughput.
- **Low-throughput, resource-heavier** (`data-export`: 2) — file generation work, deliberately not parallelized aggressively.
- **Singleton sweeps** (`retention-cleanup`, `subscription-lifecycle`, `invoice-lifecycle`, `support-session-lifecycle`, `conversation-auto-close`, `sla-escalation`: all 1) — each is a periodic, workspace-wide scan; running more than one instance concurrently would only contend with itself, not add real throughput.
- **`webhook-processing`: deliberately left unset (BullMQ's default, 1)** — not an oversight. See "A concurrency value withheld on purpose" below.

Six of the singleton sweep queues also gained `attempts: 2, backoff: {type: "exponential", delay: 60_000}` on their `queue.add()` calls — each sweep only ever operates on its own still-pending candidate set, so a retry after transient failure (a brief Mongo blip, a Redis hiccup) is safe and idempotent by construction. `data-export` was deliberately excluded from this change; see TD-059.

Every queue also gained explicit `defaultJobOptions: {removeOnComplete: {count: N}, removeOnFail: {count: M}}`, sized per queue's expected job volume (email/webhook-delivery keep more history given their volume; the sweep queues keep a few days' worth given their low frequency). Before this volume, completed/failed job records accumulated in Redis indefinitely — this is the first explicit retention policy any queue in this codebase has had.

## A concurrency value withheld on purpose: `webhook-processing`'s check-then-act race

While tuning `webhook-processing.processor.ts` toward the same treatment as `webhook-delivery` (its outbound counterpart), implementation surfaced a genuine data-integrity risk: `WebhookService.handleInboundMessage()` looks up whether a message with a given Meta-supplied `waMessageId` already exists, then inserts if not — two separate operations, not one atomic upsert. Meta's own webhook delivery guarantee is at-least-once, not exactly-once, so duplicate deliveries for the same message are a real, expected occurrence this code path already has to handle — today, safely, because concurrency=1 means there is never a second job racing the first job's own find-then-insert window. Raising concurrency here without first closing that race would have meant shipping a config change that silently introduces duplicate message records under real-world load — exactly what the Architect's own mandatory verification condition ("no queue tuning may silently introduce duplicate processing") was written to catch.

Raised via the doubt policy mid-implementation rather than decided silently either way; resolved as **keep concurrency unset, document as Technical Debt (TD-060)**. The actual fix (a unique index on `waMessageId` plus an atomic upsert) is a data-integrity change to already-shipped Communication module code, not a config tuning change, and deserves its own review.

## MongoDB: explicit, configurable connection pool and timeout values

Before this volume, `DatabaseModule`'s `MongooseModule.forRootAsync` factory passed no pool or timeout options at all — every value silently fell back to the driver's own defaults (`maxPoolSize: 100`, no explicit `minPoolSize`, driver-default timeouts). Five new configuration values (`MONGO_MAX_POOL_SIZE=10`, `MONGO_MIN_POOL_SIZE=2`, `MONGO_CONNECT_TIMEOUT_MS=10_000`, `MONGO_SOCKET_TIMEOUT_MS=45_000`, `MONGO_SERVER_SELECTION_TIMEOUT_MS=10_000`) are now read from `AppConfig` and threaded through explicitly. `maxPoolSize=10` is deliberately far below the driver's own default of 100 — a single-process API instance with the queue concurrency values above doesn't need 100 concurrent connections, and an unbounded pool size is one of the more common ways a misbehaving service can exhaust a shared Mongo deployment's own connection limit. Like the Docker resource limits (see ADR-PHD-006), these are documented as conservative, evidence-pending starting values, not final tuned numbers.

## Redis-backed rate limiting: correctness fixed, a new scaling limit found

Before this volume, `ThrottlerModule` used `@nestjs/throttler`'s default in-memory storage — meaning every API process instance (a horizontally-scaled deployment, or even PM2 running more than one worker) tracked rate limits independently, so a client's real effective limit was `N × (instance count)`, not the intended `N`. `RedisThrottlerStorageService` (`infrastructure/redis/`) replaces this with a Redis-backed Lua-script implementation, sharing one counter across every instance — verified directly: a rate-limited client's `X-RateLimit-Remaining` header decrements identically regardless of which instance serves a given request.

**A gap discovered while setting up this verification, not part of the original scope:** the API had no Express `trust proxy` configuration anywhere. Behind nginx in production (`docker-compose.prod.yml`), this meant `req.ip` — what `ThrottlerGuard` keys its per-client limit on — resolved to nginx's own single internal Docker IP for every request from every tenant, collapsing the intended per-client 300 req/60s limit into an accidental platform-wide one. `app.set("trust proxy", 1)` (`main.ts`) fixes this, trusting exactly the one reverse-proxy hop this topology actually has (nginx already sets `X-Forwarded-For` correctly, per `docker/nginx/nginx.conf`) without trusting an arbitrary chain that would let a direct, unproxied caller spoof its own IP. Verified directly: distinct simulated client IPs now get independent, correctly-isolated rate-limit counters. Raised and resolved via the doubt policy given it changes the semantics of an already-shipped security control (SEC-010), not silently patched.

**A second, deeper limit found via k6 stress testing, deliberately not fixed this volume:** the shared Redis connection (`REDIS_CLIENT`) is configured with `maxRetriesPerRequest: null` — correct and required for BullMQ's own Worker semantics, but wrong for the synchronous, hot-path `ThrottlerGuard` check reusing the same connection, which should fail fast rather than queue indefinitely under Redis pressure. At 400 concurrent simulated clients against a zero-I/O endpoint, this plausibly produced the stress scenario's 43-minute tail latency (see the Performance Report). Documented as TD-061 rather than fixed in this volume — separating the throttler's connection from BullMQ's is a real architectural change to already-shipped Infra work, on a single stress-test data point, at a concurrency level far beyond WAPP's current expected beachhead-stage traffic.

## Explicit request body-size limits

`bootstrap()` (`main.ts`) now registers `app.useBodyParser("json", {limit: "1mb"})` / `app.useBodyParser("urlencoded", {limit: "1mb", extended: true})` explicitly, via `NestFactory.create`'s `bodyParser: false` option plus manual registration — previously, every request silently relied on `body-parser`'s own undocumented 100kb default. 1mb comfortably covers every real JSON payload this API receives (file uploads bypass the body parser entirely via Cloudinary direct-upload signing, SEC-016) while still bounding an endpoint like the inbound WhatsApp webhook, which is unauthenticated until its signature is verified.

## Frontend: bundle-budget tooling, not a bundle-size fix

`@next/bundle-analyzer` is now wired into both `apps/web` and `apps/admin`'s `next.config.ts` (a `pnpm analyze` script, `ANALYZE=true next build`, generating a static treemap; a complete no-op otherwise, zero effect on a normal build or deploy). This volume did not attempt to reduce either app's bundle size — no evidence yet suggests it's a problem — it establishes the tooling and the baseline measurement (`~2.53MB`/`~1.79MB` static JS, see the Performance Report) that a future volume would need to act on. Separately, all `refetchInterval`-based TanStack Query polling in Communication's inbox/conversation/broadcast/campaign views gained explicit `refetchIntervalInBackground: false` — a backgrounded browser tab no longer keeps polling the API, a real, if modest, load reduction with no user-visible behavior change (foreground polling is unaffected).

## The API_CPU_LIMIT evidence trail

`docker-compose.prod.yml`'s `API_CPU_LIMIT` default was approved and shipped at a conservative `1.0` pending real load-test evidence, exactly as the Architect's own resolution specified. k6 testing produced that evidence directly: 30 concurrent `/api/v1/auth/register` calls (bcrypt cost factor 12 — a legitimate, OWASP-range security default, not something to weaken for throughput) measured p95=20.92s at 1.0 CPU, p95=6.46s at 2.0 CPU, p95=3.66s at 4.0 CPU. The 1.0→2.0 step captured the largest relative gain (3.2×) before returns diminished sharply; the default is now `2.0`. Full methodology and numbers are in the Performance Report, not repeated here — this ADR records the decision and its evidentiary basis, not the raw data.
