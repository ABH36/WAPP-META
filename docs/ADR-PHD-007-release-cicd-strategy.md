# Release & CI/CD Strategy

**Status:** Accepted
**Date:** 2026-08-17
**Scope:** PHD-001 Volume-4 (Release Readiness, CI/CD & Deployment) — the CI-pipeline and versioning half of the volume. See `docs/ADR-PHD-008-production-deployment-rollback-strategy.md` for deployment topology, ordering, rollback, and disaster-recovery.
**Implemented in:** `.github/workflows/{ci,commitlint}.yml`, `docker-compose.prod.yml`, `apps/api/src/{main.ts,config/configuration.ts}`, `docs/DEPENDENCY-AUDIT-phase1.md`, `docs/RELEASE-RUNBOOK.md`, `docs/RELEASE-CHECKLIST.md`

## The central architectural decision: CI verifies, a human deploys

Before any of this volume's own work, this repository already had no deployment automation of any kind — no SSH credentials in CI, no container registry, no deploy step anywhere. The Architecture Review's central question was whether Volume-4 should build real continuous deployment (CI gains VPS credentials, auto-deploys on merge/tag) or keep CI as a quality gate with a human executing a documented Release Runbook. **Resolved: the latter.** Given the single-VPS Hostinger topology (TAD-001 DEP-001/002/003), the complete absence of any registry or deploy-credential infrastructure today, and that introducing either is a materially larger commitment than "harden the release process for what already exists," automating deployment now would be building new infrastructure without evidence it's needed — the same discipline already applied to deferring the Worker/API process split in PHD-001 Volume-3. This decision also settled a related question raised during the same review (whether to migrate `apps/web`/`apps/admin` to Vercel and `apps/api` to Render): kept on the current frozen topology, since that migration would itself be a significant re-architecture, not a release-hardening change, and was explicitly deferred as a possible future TAD-001 amendment, not folded into this volume.

## CI pipeline: what already existed, and what this volume actually added

`.github/workflows/ci.yml` already ran lint/typecheck/test/build (matrix across `api`/`web`/`admin`) on every PR and push to `main` before this volume began — not a green-field build. Two things were wrong with it, both fixed:

- **Toolchain drift, a real pre-existing bug, not a hypothetical.** Both `ci.yml` and `commitlint.yml` hardcoded Node 20/pnpm 9, while root `package.json` has required Node 22.13+/pnpm 11.20.0 since PHD-001 Volume-3 (`pnpm@11.20.0` needs Node 22's built-in `node:sqlite`). CI would have been running a toolchain the application itself no longer supports. Both workflows now pin Node 22/pnpm 11.
- **Two entire categories of verification never ran in CI at all**: Docker image builds (§12) and Playwright e2e (§11) — both existed as real, working local capabilities (Volume-3's manual Docker verification; the e2e suite itself, `pnpm test:e2e`) but neither was wired into the automated pipeline.

**New jobs added, all verify-only (none deploy anything):**

- `security-audit` — `pnpm audit --audit-level=critical` on every PR/push. Fails only on a **new** critical finding, matching the bar PHD-001 Volume-1 already established: re-running the audit before wiring this in found the exact same `0 critical, 15 high, 20 moderate, 5 low` as Volume-1's last documented pass — no drift, nothing new to review. Failing CI on the already-reviewed high/moderate/low findings would just make every future PR red for a decision already made (see `docs/DEPENDENCY-AUDIT-phase1.md`'s 2026-08-17 update).
- `e2e` — installs Playwright's own browser binaries, runs `pnpm test:e2e`. Playwright's own `webServer` config boots `apps/web`/`apps/admin` itself and exercises only the public/unauthenticated surface — no database, Redis, or `apps/api` instance needed, per the suite's own existing design.
- `docker-verify-api` / `docker-verify-web` / `docker-verify-admin` — three separate jobs, not one matrix, since `apps/api` genuinely needs live Mongo/Redis service containers to boot and the two frontends need neither (a shared matrix would start unused service containers for two of every three runs). Each builds the real production Dockerfile, boots the container, and polls its healthcheck endpoint until it responds or a timeout is hit. `docker-verify-api` additionally verifies graceful shutdown produces exit code 0 (`docker stop` — the same behavior PHD-001 Volume-3 verified manually, now automated on every push).

## Versioning: SemVer, git tags, no new tooling

Every package in this monorepo has been frozen at `0.1.0` since inception — no version has ever been bumped, no git tag has ever been cut. This volume establishes the convention without cutting a production release itself (that happens after Final QA, per the document's own `PHD Complete → Final QA → Production Deployment → v1.0` sequence — cutting `v1.0.0` now would be presumptuous of a gate this volume explicitly does not cross).

**The convention:** annotated, immutable Git tags in `vMAJOR.MINOR.PATCH` form. Bump decisions follow the same Conventional Commits vocabulary this repository already enforces via `commitlint` (`feat` → minor, `fix` → patch, a `BREAKING CHANGE` footer → major) — a human judgment call at release time, not an automated tool. No `semantic-release`/`standard-version`-class dependency is introduced: this repository's commit volume and release cadence don't yet justify that automation, and it would be new infrastructure adopted without the evidence this project's own discipline requires elsewhere. `git tag -a vX.Y.Z -m "..."` (never `-f`/force-moved, never a lightweight tag) and an explicit `git push origin vX.Y.Z` are the only two commands involved; both are steps in the Release Runbook, executed by a human, matching the "CI verifies, a human deploys" decision above.

**Version/commit exposure (§14) already had its own mechanism, just never wired up.** `BUILD_VERSION`/`GIT_COMMIT` env vars have existed since PHD-001 Volume-2 (read into `AppConfig.observability`, surfaced via `/settings/diagnostics` and OpenTelemetry's `service.version` attribute) — but nothing ever set them: not the Dockerfiles (despite `configuration.ts`'s own comment claiming they were "baked in at Docker build time," which the Dockerfile never actually implemented), not `docker-compose.prod.yml`. Every real deployment to date would have silently reported `"unknown"` for both. Fixed by adding them to `docker-compose.prod.yml`'s `api` service `environment:` block, computed fresh from the actual git state by the Release Runbook immediately before each deploy — consistent with the "no registry, image rebuilt from source at each deploy" decision above, since there's no meaningful difference between "baked in at build time" and "set at container start" when both happen from the same git checkout at the same moment.

**Deployment events are now observable through the existing structured-logging stack (§35).** The API's own successful-boot log line and the `bootstrap.failed` structured log (PHD-001 Volume-3's Must Fix #4) both now carry `event`, `buildVersion`, `gitCommit`, and `environment` fields — no secrets, matching §35's explicit prohibition. "Deployment start" has no clean equivalent inside the application itself (the process doesn't exist yet when a deployment starts) — that event is a Release Runbook procedural step, not application code.

## What was deliberately not built

- **No container registry.** Consistent with the "no automated CD" decision — an artifact registry's main value (pull a specific pre-built image without rebuilding) doesn't apply when the VPS always builds fresh from the exact git commit/tag the operator checks out.
- **No SBOM or image signing.** TD-056 remains open and unapproved; introducing either now would be exactly the "silently introduce a new signing architecture" this volume's own planning document explicitly prohibited.
- **No affected-package/workspace-aware CI test selection.** `pnpm -r test`/`-r build` runs everything, every time — fine at this repository's current size; worth revisiting only if CI duration becomes a real, measured cost.
