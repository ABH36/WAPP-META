# Settings UI Strategy

**Status:** Accepted
**Date:** 2026-08-12
**Scope:** FRD-001 Volume-7 — Settings UI. How `apps/web` implements Settings navigation, personal preference synchronization, Integrations, and permission rendering on top of the frozen Settings backend (PRD-006), without duplicating what FRD-001 Volume-2/Volume-3 already shipped.
**Implemented in:** `apps/web/src/{features/settings,services,types/settings.ts,lib/preference-sync.ts,stores/theme-store.ts,stores/ui-store.ts}`, `apps/web/src/app/(workspace)/settings`, `packages/ui/src/components/{settings-section,preference-card,integration-card,api-key-card,webhook-card,export-job-card,health-status-card}.tsx`

## Settings navigation: a hub, not a rebuild

Cross-referencing this volume's planning document against the real, already-shipped app tree found that 5 of the 12 named modules already exist: Workspace Settings (`/workspace/profile`, `/workspace/business-hours`) and Branding (`/workspace/branding`) from FRD-001 Volume-3, Change Password/Active Sessions/Login History (`/profile/security`, `/profile/sessions`, `/profile/login-history`) from FRD-001 Volume-2, and Workspace Notifications (`/workspace/notifications`) also from Volume-3 — every one of them hitting the identical `/settings/*` and `/workspaces/me/*` PRD-006 routes this volume would otherwise target again. Per the Architect's approval ("Settings Home becomes a navigation hub rather than a duplicate implementation"), `settings-home.tsx` composes only read-only summaries (workspace name, theme, language, timezone, currency, branding preview) plus Quick Links to both the existing pages and the six genuinely new sections — no forms, no writes, and critically, no new routes shadowing what Volume-2/Volume-3 already own. The Settings sidebar group (`workspace-sidebar.tsx`) reflects this exactly: 8 sub-items, not 12.

## Preference synchronization: Theme/Sidebar/Density migrated off localStorage-only state

A complete per-user preferences backend (`GET/PATCH settings/user/*`) existed but was entirely unconsumed by the frontend — `theme-store.ts`/`ui-store.ts` (FRD-001 Volume-1) were pure client-side Zustand stores with no backend counterpart. Per the Architect's explicit approval ("Cross-device persistence is now the authoritative behaviour"), both stores were migrated: `theme-store.ts`'s `Theme` type changed from a local `"light"|"dark"|"system"` string union to the real `@wapp/shared-types` `Theme` enum, and `ui-store.ts` gained a `density: UiDensity` field. `lib/preference-sync.ts` is the seam — `hydrateUserPreferences()` overwrites local/cached state with the real backend value once a session is established (called from both `auth-provider.tsx`'s silent-refresh hydration and `login-form.tsx`'s fresh-login path), and `syncTheme`/`syncSidebar`/`syncDensity` write through to the backend on every user-initiated change (`workspace-header.tsx`'s toggle buttons, `preferences-view.tsx`'s controls). Every sync call is deliberately best-effort (a caught, silently-swallowed rejection) — a failed write never blocks the UI interaction that triggered it; the local Zustand state (still localStorage-persisted as a fast-first-paint cache) remains the fallback of record.

## Integrations: three independent services, no WhatsApp Connect

`IntegrationsController`'s own `GET settings/integrations` composition confirmed there is no generic Integration CRUD abstraction on the backend — WhatsApp, Email, and Third-party Apps are three unrelated services stitched into one read-through DTO, and `integrations-view.tsx` mirrors that exactly rather than inventing a uniform model. WhatsApp's "Connect" action was scoped out during implementation research: the real `POST communication/whatsapp/connect` route requires a `code`/`wabaId`/`phoneNumberId` payload only obtainable through a genuine Meta Embedded Signup flow (Facebook JS SDK, an OAuth popup, `postMessage` handshake) — a substantial standalone integration with no Meta App ID or SDK configuration present anywhere in this app. Per the Architect's approval, this screen shows WhatsApp's current connection status read-only and supports Disconnect/Test Connection/Refresh Metadata (all of which act on an already-connected WABA); the full Embedded Signup build is filed as Technical Debt.

## Security presentation: unchanged, confirmed not touched

No Security-related code was written this volume. `/profile/security`, `/profile/sessions`, and `/profile/login-history` (FRD-001 Volume-2) remain the canonical, sole implementation — `settings-home.tsx` links to them, nothing more. This ADR records that explicitly so a future volume doesn't rediscover the same overlap this Architecture Review found.

## Permission rendering: `EDIT_WORKSPACE`/`VIEW_REPORTS`, self-scoped Preferences

Every new screen follows the established `useHasPermission` (read) / `useHasFullPermission` (write) split, hidden entirely rather than a restricted placeholder. Integrations/API Keys/Webhooks/Audit Logs/Data Export all gate on `EDIT_WORKSPACE` (binary — Owner/Administrator=FULL, every other role=NONE, confirmed against `permission-matrix.ts`); Diagnostics deliberately uses the looser `VIEW_REPORTS`, matching the backend's own `SystemAdminController` doc-comment distinguishing it from Audit Logs' tightened, security-sensitive gate. Preferences is the one screen with no permission check at all — `UserPreferencesController` has no `@RequirePermission` decorator, only the global `JwtAuthGuard` (every user manages their own account), and `settings-home.tsx`'s Quick Links filter each link by the same permission its target screen actually requires, never a single all-or-nothing Settings gate.
