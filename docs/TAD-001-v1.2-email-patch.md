# TAD-001 v1.2 — Email Architecture Patch

**Applies to:** TAD-001 (adds a new §11A, between Authentication Standards and API Standards, since email is load-bearing infrastructure for Authentication per PRD-002 GBR-002)
**Status:** Final Review

---

## 11A. Email Architecture

### Provider Decision: Resend

| Criterion                  | Why Resend                                                                                                                                                                                                                                                                                                                             |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Developer experience       | First-class Node.js/TypeScript SDK, integrates cleanly with NestJS without a heavy wrapper — consistent with TPH-003 (Convention over Configuration)                                                                                                                                                                                   |
| Deliverability             | Built on top of AWS SES infrastructure with modern deliverability tooling (DKIM/SPF/DMARC managed through the dashboard) — important given email verification (GBR-002) sits on the critical path of Decision 015's 30-minute activation metric; a deliverability failure here directly threatens that already-approved success metric |
| React Email support        | Native support for React Email templates — lets the same component model (React) used across the rest of the stack (Next.js) author transactional emails, rather than maintaining a separate templating language                                                                                                                       |
| Pricing model at MVP scale | Free tier covers Phase-1 volume comfortably; scales predictably, consistent with the cost-discipline already established for Hostinger VPS (TAD-001 DEP-006)                                                                                                                                                                           |
| Alternative considered     | AWS SES directly — rejected for Phase-1: lower-level, more setup/operational overhead for the same outcome at current scale; Resend can be swapped for direct SES later without changing the calling code, since it's abstracted behind a single `EmailService` (see below)                                                            |

### Architecture Integration

Email sending is a **cross-cutting capability**, following the same pattern already established for Notifications (ARCH-001) and Audit — domains publish an "email needed" event; a dedicated `EmailModule` owns delivery, templates, retries, and provider integration. No business module calls Resend directly.

```
Identity/Billing/Collaboration (business modules)
        │  publish event (e.g. EmailVerificationRequested)
        ▼
   EmailModule (queues via BullMQ)
        │
        ▼
   Resend API
```

This keeps the provider swappable (TAD-001 TPH-002 modularity) and keeps business modules ignorant of email delivery mechanics, consistent with SAD-002 DB-009/010 (business logic independent of infrastructure).

### Queue Integration (BullMQ)

All email sends are queued, never sent synchronously in the request/response cycle — consistent with TAD-001's existing queue-workload list ("Email sending" is already named there). This matters specifically for Authentication: registration should not block on Resend's API responding before returning success to the client.

- **Retry strategy:** 3 attempts, exponential backoff (10s / 60s / 5min), per BullMQ's built-in retry support (already an approved TAD-001 technology decision).
- **Failure handling:** after 3 failed attempts, the job moves to a dead-letter state, an internal alert fires (Platform Alerts, per PRD-007 Vol 3 Module E pattern — "Webhook Issue"-style alert extended to cover email delivery failure), and — specifically for Email Verification and Password Reset — the user-facing UI offers an explicit "Resend" action rather than leaving them stuck with no recourse (this was already a named business requirement — EMAIL-BR-004, PRD-002 Part 2).

### Development vs. Production Behavior

| Environment | Behavior                                                                                                                                        |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Development | Emails route to Resend's test mode / a fixed test inbox (no real delivery); email content is also logged to console for fast local iteration    |
| Staging     | Real delivery, but restricted to allow-listed test recipient addresses only — prevents accidental delivery to real customer addresses during QA |
| Production  | Full delivery, full retry/dead-letter handling, full Platform Alert monitoring active                                                           |

### Email Flows (traced to approved requirements — no new business behavior introduced)

| Flow                              | Trigger                                     | Traces to                                                                                         |
| --------------------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| **Email Verification**            | Registration complete                       | PRD-002 GBR-002 (mandatory before login), EMAIL-BR-001–005                                        |
| **Password Reset**                | Forgot Password request                     | PRD-002 Part 2 §D, PASS-BR-001–004                                                                |
| **Workspace/Team Invitation**     | Owner/Admin invites a user                  | PRD-002 Part 3A Module A                                                                          |
| **Trial Ending Reminder**         | Configurable days before trial expiry       | PRD-005 Notification Events ("Trial Ending")                                                      |
| **Payment Failure Reminders**     | Day 3 / Day 5 / Day 7 of grace period       | ADR-018 (7-day grace period schedule) — reuses the exact schedule already approved, not a new one |
| **Invoice / Receipt**             | Successful payment, invoice generated       | PRD-005 Module G, PRD-007 Vol 2 Module C                                                          |
| **Subscription Renewal Reminder** | Configurable days before renewal            | PRD-005 Notification Events ("Renewal Reminder")                                                  |
| **Support Session Notification**  | Temporary Support Access requested/approved | PRD-007 Vol 3 Module B                                                                            |

No flow above is new — each already existed as a named Notification Event or Business Requirement in an approved PRD; this patch only defines _how_ they get delivered.

### Email Templates

Built with **React Email**, stored in `packages/email-templates`, shared between the `EmailModule` (server-side render + send) and — where useful — a preview route in the admin app for QA. Every template inherits a shared layout component enforcing:

- WAPP wordmark + consistent header/footer (matches DS-001 brand tokens, not a separately-invented email visual style)
- Plain-text fallback generated automatically from the React component (accessibility + deliverability best practice)
- No tracking pixels beyond what Resend provides natively for delivery/open metrics — no third-party email trackers, consistent with the platform's general privacy stance (D019, PRD-008 Trust Center)

### Required Environment Variables

```
RESEND_API_KEY=
RESEND_FROM_ADDRESS=            # e.g. no-reply@wapp.io (requires domain verification in Resend)
RESEND_FROM_NAME=WAPP
EMAIL_VERIFICATION_TOKEN_TTL=   # minutes, configurable per EMAIL-BR-002
PASSWORD_RESET_TOKEN_TTL=       # minutes, per PASS-BR-002
EMAIL_TEST_MODE=                # true in dev/staging
EMAIL_TEST_RECIPIENT_ALLOWLIST= # comma-separated, staging only
```

Per TAD-001 SEC-007 / DEP-005: these are never committed to source control, and `RESEND_API_KEY` is treated as a Tier-1 secret (same handling class as the JWT signing secret and MongoDB connection string).

## Consistency Statement

This patch introduces one new technology decision (Resend) and one new module (`EmailModule`) within the already-approved Modular Monolith and cross-cutting-service pattern (ARCH-001). It defines no new business requirement — every email flow listed traces to a Notification Event or Business Requirement that was already approved in PRD-002, PRD-005, or PRD-007.
