# Platform Support & Break-Glass Access Boundary

**Status:** Accepted
**Date:** 2026-08-10
**Scope:** PRD-007 Volume-3 — Platform Support, Break-Glass Access & Global Audit. How a Platform Administrator gets time-boxed, audited access to a specific tenant's data without becoming that tenant's user, and without any silent bypass of the approval step.
**Implemented in:** `apps/api/src/modules/platform/schemas/support-session.schema.ts`, `repositories/support-session.repository.ts`, `services/platform-support-sessions.service.ts`, `services/platform-support-workspace-overview.service.ts`, `guards/support-session.guard.ts`, `controllers/platform-support-access.controller.ts`, `platform-support-sessions.controller.ts`, `platform-support-workspace.controller.ts`, `queue/support-session-lifecycle.processor.ts`

## Read-only, not Impersonation — resolved from §9, not §4

§4.4 and §8 both name "Impersonation" (`IMPERSONATION_STARTED`/`ENDED`) as if it were a live capability this volume ships. §9's literal API surface says otherwise: every route under `/platform/support/*` is a `GET`, a session lifecycle action (`request`/`approve`/`start`/`end`), or a read of the audit/investigation views — there is no route anywhere that lets a Platform Administrator write to a tenant's CRM, Billing, or Communication data, or obtain a token that acts as a tenant user. This is the same §9-is-the-authoritative-shipped-surface reasoning already applied in Volume-2 (TD-022, Invoice Regenerate/Reissue) and Volume-1 before it — where the document's prose names more than its route table delivers, the route table wins and the gap is deferred, not guessed at.

This reading is reinforced structurally by BR-004: "Platform users never become tenant users" was already a hard guarantee before this volume existed (ADR-PLAT-002's fully separate identity/auth/guard systems — `PlatformAuthGuard`/`PlatformPermissionsGuard` operate on `AuthenticatedPlatformUser`, never `AuthenticatedUser`, and there is no code path anywhere that mints a tenant-shaped token for a platform identity). A real Impersonation feature — issuing a token that lets a Platform Administrator act as a specific tenant user — would be the first feature in this codebase to intentionally blur that boundary. Building it inside a volume whose own document gives it zero write-capable routes, no consent/notification mechanism, and no legal/compliance sign-off would mean inventing all of that unreviewed. `IMPERSONATION_STARTED`/`ENDED` were deliberately left out of `domain-events.ts` rather than added-but-unused, with a comment pointing here.

What this volume ships instead: `GET /platform/support/workspaces/:id` (`PlatformSupportWorkspaceOverviewService.getOverview`) composes a read-only snapshot — Workspace, Users (via `WorkspaceService`'s own `toMemberSummary`, reused directly, not duplicated), Subscription, Invoices, and Settings' branding/preferences overview — gated behind an active Support Session. No CRM (Customer/Lead/Deal/Conversation) surface is exposed at all; §12 names cross-tenant CRM/Billing _search_ as still out of scope, and this volume's read surface stays inside that line deliberately.

## Settings read scope: branding/preferences only, not the full Audit Log

`PlatformSupportWorkspaceOverviewService` calls `SettingsService.getOverview()` — the same branding/preferences aggregate a tenant Owner sees, not `AuditLogService`. Settings' own `AuditLogEntry` collection is a tenant-internal record of who-changed-what-within-the-workspace; pulling all of it into every Support workspace overview would mean every Break-Glass read silently doubles as a full tenant audit-log export, a materially larger disclosure than "let a Support agent see this tenant's plan and branding while helping them." The Investigation Timeline (`PlatformInvestigationService`, see ADR-PLAT-006) is the deliberate, narrower channel for audit-log-shaped data — and even there, it's scoped to entries relevant to a specific investigation, not a blanket export. `SettingsModule.exports` was widened to `[SettingsService, AuditLogService]` for this volume; `AuditLogService` is exported because the Investigation Timeline needs it directly, not because the workspace overview does.

## `startedBy`, not `requestedBy`, gates live access

The approved permission model splits Break-Glass into two distinct actors: any of the three platform roles can _request_ access (`REQUEST_SUPPORT_ACCESS`, `FULL` for all three), but only `PLATFORM_SUPER_ADMIN` can _approve_ (`APPROVE_SUPPORT_ACCESS`) and _start_ (`START_SUPPORT_SESSION`) it. That means the person who requested access and the person who is actually granted live access can be different people — a Support Executive can request; only a Super Admin's own `start()` call produces a session that's actually live.

`SupportSession` was designed with this split from the outset — `requestedBy` and `startedBy` are two separate fields, and every live-access check (`SupportSessionRepository.findActiveForWorkspaceAndUser`, called from `SupportSessionGuard`) gates on `startedBy`, never `requestedBy`. Gating on `requestedBy` instead would have let the _requester_ read tenant data even if a different Super Admin approved and started the session — backwards from what "approval" is supposed to mean. This was corrected during design, before any repository code was written, not discovered as a bug afterward.

## Approval has no bypass, by construction

§6 and the Architecture Review both require every Break-Glass grant to go through explicit Super-Admin approval — no self-approval, no auto-approval path, no "urgent" shortcut. This is enforced by the session's own state machine rather than by a business-rule check that could be individually forgotten at a call site: `PlatformSupportSessionsService.start()` only operates on a session already in `APPROVED` status (`SupportSessionRepository.approve()` is the only path from `REQUESTED` to `APPROVED`, and it's a separate permission — `APPROVE_SUPPORT_ACCESS` — from `START_SUPPORT_SESSION`). There is no method anywhere in the service that transitions `REQUESTED` directly to `ACTIVE`. A Super Admin can approve their own request (nothing in §6 requires a _second_ Super Admin), but they cannot skip the approval step itself — `start()` on a `REQUESTED` session throws, the same way `update()` on a `CLOSED` Support Ticket throws in Volume-2.

## Real-time expiry check, not just the sweep

`SUPPORT_SESSION_MAX_DURATION_MINUTES = 240` (§10) is enforced at `start()` by computing `expiresAt = new Date(Date.now() + durationMinutes * 60_000)`, capped to the 240-minute ceiling. A repeatable BullMQ job (`SupportSessionLifecycleProcessor`, mirroring `SubscriptionLifecycleProcessor`'s existing shape exactly, sweep interval `SUPPORT_SESSION_LIFECYCLE_SWEEP_INTERVAL_MS = 5 * 60 * 1000`) periodically flips overdue `ACTIVE` sessions to `EXPIRED` — but the guard that actually gates every tenant-data read never trusts `status` alone. `SupportSessionRepository.findActiveForWorkspaceAndUser()` queries `{workspaceId, startedBy, status: ACTIVE, expiresAt: {$gt: new Date()}}` — a session whose sweep hasn't run yet is still correctly denied, because the expiry check happens live, at the point of access, not just at the point of bookkeeping. The sweep's only job is keeping `status` accurate for reporting/audit/list views; it is never the thing standing between an expired grant and a live tenant-data read. This generalizes the same pattern Billing's `suspendExpiredGracePeriods` sweep already established for `SubscriptionStatus` (ADR-BILL-002) — a periodic sweep for bookkeeping accuracy, plus an independent real-time guard for anything security-sensitive.

## Naming discipline: three different "session"/"support" concepts

The Architect's own Engineering Notes flagged this explicitly (after it was independently raised in this volume's architecture review): `PlatformSession` (Volume-1 — a platform staff member's own login session), `SupportSession` (this volume — a time-boxed, audited grant of cross-tenant read access), and `SupportTicket` (Volume-2 — a customer support case with no data-access implication at all) share vocabulary but are three structurally unrelated collections with no foreign-key relationship between any pair of them. A `SupportSession` does not require an open `SupportTicket`, and ending a `SupportTicket` has no effect on any `SupportSession`. This is recorded here specifically so a future reader doesn't assume a relationship that was never built.
