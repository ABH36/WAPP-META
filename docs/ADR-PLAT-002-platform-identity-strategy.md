# Platform Identity Strategy

**Status:** Accepted
**Date:** 2026-08-08
**Scope:** PRD-007 Volume-1 §6 — how Platform Administrators authenticate, and why that system shares nothing with tenant Identity
**Implemented in:** `apps/api/src/modules/platform/schemas/platform-user.schema.ts`, `platform-session.schema.ts`, `services/platform-password.service.ts`, `services/platform-token.service.ts`, `services/platform-auth.service.ts`, `services/platform-users.service.ts`, `guards/platform-auth.guard.ts`, `guards/platform-permissions.guard.ts`, `decorators/require-platform-permission.decorator.ts`, `packages/shared-types/src/permissions/platform-permission*.ts`

## The decision: implemented independently, not extended from Identity

§6 states Platform Administration must be "completely isolated" — "a Workspace Owner can never access Platform Administration." The Architecture Review resolved (Question 2) that this isolation is best guaranteed structurally, not just by a permission check: a genuinely separate identity system, duplicated in shape but never shared in code, rather than tenant `User` extended with a platform flag. A shared `User` model would mean one JWT secret compromise, one password-hashing code path, and one session table cover both a customer's workspace login and platform-staff access to every tenant's data — a single point of failure this ADR exists to avoid.

## What's duplicated, and why each duplication is deliberate

| Tenant (Identity)                                           | Platform (this volume)                                                               | Why not shared                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `User` (`users` collection)                                 | `PlatformUser` (`platform_users`)                                                    | No `workspaceId` relationship at all — `PlatformUser` isn't a kind of `User`, it's a different kind of thing. Provisioned by an existing `PLATFORM_SUPER_ADMIN` only (`PlatformUsersService.create()`), never self-registered — no email verification, no password-reset self-service, no registration endpoint exist for it, all deliberate scope trims for a small, internal-staff-only user base.                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `Session`                                                   | `PlatformSession` (`platform_sessions`)                                              | Exact structural mirror (`platformUserId`, `jti`, `tokenHash`, TTL-indexed `expiresAt`, `revokedAt`/`replacedByJti` for rotation tracking) — but a separate collection, so revoking every tenant session for a compromised account can never accidentally touch a platform session and vice versa.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `PasswordService` (bcrypt wrapper)                          | `PlatformPasswordService`                                                            | A small, genuinely stateless wrapper — duplicating ~10 lines was judged safer than importing a tenant-module service into Platform. Both read the same `auth.bcryptSaltRounds` config number, which is a non-secret cost factor, not a credential — the one piece of config sharing that isn't a security-relevant coupling.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `TokenService`                                              | `PlatformTokenService`                                                               | Same `parseDurationToSeconds` helper duplicated, same sign/verify shape — but reads `config.get("platformJwt")`, a completely separate secret pair (`PLATFORM_JWT_ACCESS_SECRET`/`PLATFORM_JWT_REFRESH_SECRET`, distinct env vars, `.env.example` carries an explicit comment: "Never reuse the same value across the two pairs, even in dev"). Every payload carries `type: "platform_access"`/`"platform_refresh"`, distinct from the tenant `"access"`/`"refresh"` discriminators — a tenant JWT is rejected by `PlatformTokenService.verifyAccessToken()` at the signature-verification step (wrong secret), not merely by a role check, and a platform JWT is equally rejected by the tenant `TokenService`. This was verified directly: see `platform-token.service.spec.ts`'s "rejects a tenant access token even if somehow signed with the same secret" case. |
| `JwtAuthGuard` / `PermissionsGuard`                         | `PlatformAuthGuard` / `PlatformPermissionsGuard`                                     | Mirror the tenant guards' exact shape (extract Bearer token → verify → populate `request.platformUser` / read a `@SetMetadata`-declared required permission → check a matrix) but are never merged with them — see "the global-guard hazard" below for why this split is load-bearing, not cosmetic.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `Permission` / `PERMISSION_MATRIX` / `getPermissionLevel()` | `PlatformPermission` / `PLATFORM_PERMISSION_MATRIX` / `getPlatformPermissionLevel()` | The tenant matrix is hard-typed to `TenantRole` — coercing a `PlatformRole` through it would either fail to compile or, worse, silently resolve a missing matrix key to `undefined` rather than `PermissionLevel.NONE` (a silent-authorization-failure risk). A fully parallel, independently-typed matrix removes that risk entirely, and matches §7's own "Workspace Permission Matrix remains unchanged" instruction.                                                                                                                                                                                                                                                                                                                                                                                                                                               |

## `PlatformRole` reuse: the one thing that was _not_ independently invented

§7 of the relayed document proposed new role names (`PLATFORM_ADMIN`/`SUPPORT_ENGINEER`/`BILLING_OPERATOR`). `packages/shared-types/src/enums/role.enum.ts` already contained a `PlatformRole` enum — `PLATFORM_SUPER_ADMIN`/`PLATFORM_SUPPORT_MANAGER`/`PLATFORM_SUPPORT_EXECUTIVE` — scaffolded during planning under already-approved ADR-032 (mandatory "Platform" prefix on any platform-scoped role name) and ADR-036 (which explicitly removed a billing-specific platform role for Phase-1). This was flagged as an explicit conflict rather than silently picking either name set (Question 1), and resolved to reuse the existing enum as-is. `PLATFORM_PERMISSION_MATRIX` grants FULL access to every `VIEW_*` permission for all three roles; every `MANAGE_*` permission is FULL for `PLATFORM_SUPER_ADMIN` only, except `MANAGE_ANNOUNCEMENTS`, where `PLATFORM_SUPPORT_MANAGER` also gets FULL and `PLATFORM_SUPPORT_EXECUTIVE` gets VIEW_ONLY — the one permission where a non-Super-Admin role has any write access at all.

## The global-guard interception hazard

`JwtAuthGuard` and `PermissionsGuard` are registered as global `APP_GUARD`s inside `IdentityModule` (not `AppModule`) — confirmed by reading `identity.module.ts` directly — so they run on **every route in the entire application**, including every Platform route, unless a route is explicitly marked `@Public()`. Left unhandled, this would mean a Platform request needs a _valid tenant_ JWT just to reach `PlatformAuthGuard` at all — exactly backwards. Every Platform controller therefore applies `@Public()` at the class level (bypassing the tenant guard pair entirely) and then `@UseGuards(PlatformAuthGuard, PlatformPermissionsGuard)` immediately after (enforcing platform auth in its place). This is not a hypothetical: the first e2e run against a real boot caught a request with a tenant access token being correctly rejected with `401` at `PlatformAuthGuard` (wrong secret, not a missing-permission `403`) — see `test/platform.e2e-spec.ts`, "rejects a tenant access token against a Platform route."

## What deliberately isn't here

No self-service password reset, no email verification, no MFA, no OAuth — this is a small, internal, staff-provisioned user base, and every one of those is either out of scope per §12 or would be premature infrastructure for a user base measured in tens of accounts, not thousands. If Platform Administration ever grows a public-facing or larger-scale staff onboarding need, revisit this ADR before adding any of them piecemeal.
