# Platform Analytics Strategy

**Status:** Accepted
**Date:** 2026-08-10
**Scope:** PRD-007 Volume-4 §4.1/§4.2/§4.4/§4.5/§4.7 — Platform Analytics Dashboard, Operational Reports, Compliance Dashboard, Platform KPIs, Compliance Export. How the cross-cutting analytics/compliance layer composes every prior volume's data without duplicating aggregation logic or inventing values with no real source.
**Implemented in:** `apps/api/src/modules/platform/services/platform-analytics.service.ts`, `platform-reports.service.ts`, `platform-compliance.service.ts`, `platform-kpis.service.ts`; `apps/api/src/modules/platform/schemas/platform-login-history-entry.schema.ts`, `repositories/platform-login-history.repository.ts`

## Analytics Dashboard coexists with Volume-1's Dashboard, doesn't replace it

`GET /platform/dashboard` (Volume-1, frozen) and `GET /platform/analytics` (this volume) overlap substantially in subject matter — both report Total Workspaces, status breakdowns, CRM counts, and total revenue. Rather than deprecate or fold one into the other (a change to a frozen route this volume was never asked to make), `PlatformAnalyticsService` extends the exact same underlying repository methods Volume-1's `PlatformDashboardService` already established (`WorkspaceRepository.countAll/countByStatus`, `MessageRepository.countAll`, `BillingReportsService.getPlatformRevenueTotal`) rather than computing any of them a second, independent way. The two dashboards deliberately coexist: Volume-1's is the original operational at-a-glance view; this volume's is the fuller cross-tenant analytics view, adding Platform Users, Active Platform Sessions, and a CRM Growth/Revenue Summary shape Volume-1 never had.

## Storage Usage and API Usage: excluded, not stubbed

§4.1 named these two metrics, but TD-013 already deferred exactly this pair of counters (alongside Campaigns) pending commercial approval, per this engagement's standing rule to never invent or persist an unsigned-off commercial value — not even as `0`, since a displayed `0` reads as "confirmed zero usage," a real assertion nobody has approved. Architecture Review, 2026-08-10, confirmed: "Storage Usage and API Usage analytics remain out of scope. Their implementation continues to follow the existing TD-013 commercial deferral. No placeholder counters or inferred values shall be introduced." `PlatformAnalyticsSnapshot` simply has no field for either — not a `null`-valued one, an absent one, verified by e2e (`expect(snapshot).not.toHaveProperty("storageUsage")`).

## Operational Reports: an orchestration layer over 5 existing cross-tenant list methods, not a third report engine

§4.2 names 6 report types. Every one composes an existing, already-cross-tenant Platform-side method built in Volumes 1–3 — `PlatformReportsService` introduces no new aggregation logic, only new row-shaping and CSV/Excel serialization:

| Report type        | Source                                                                   |
| ------------------ | ------------------------------------------------------------------------ |
| WORKSPACE          | `WorkspaceRepository.listAllForPlatform` (Volume-1)                      |
| BILLING            | `InvoiceService.listAllForPlatform` (Volume-2)                           |
| PLATFORM_ACTIVITY  | `PlatformAuditRepository.list` (Volume-3)                                |
| SUPPORT_OPERATIONS | `SupportTicketRepository.list` (Volume-2)                                |
| BREAK_GLASS        | `SupportSessionRepository.list` (Volume-3)                               |
| COMPLIANCE         | `PlatformComplianceService.getSnapshot` (this volume, flattened to rows) |

CSV/Excel serialization is a third copy of the same `toCsv`/`toExcelBuffer` shape Billing's and CRM's Reports services each already have — not a duplication of _reporting logic_ (each type's underlying data comes from code that already existed), but a genuinely new row shape for genuinely new report content, the same reasoning ADR-PLAT-004 used for `SupportTicketCategory` being a new taxonomy rather than a reused one. Extracting a shared CSV/Excel helper was considered and rejected: it would mean modifying Billing's and CRM's private serialization methods (both frozen modules) to share an abstraction, for a benefit (avoiding ~40 lines of duplicated but simple serialization code) that doesn't justify touching two frozen modules' internals.

`GET /platform/reports/export`'s `from`/`to` date-range filtering is a client-side filter over a bounded page (500 rows) fetched from each source — not a true range-scoped database query. This is an accepted simplification, not a defect: none of the 5 underlying list methods this volume reuses support server-side date filtering today, and adding it to all 5 (three of which live in other modules, two frozen) would be materially more invasive than the reporting feature itself warrants at current data volumes. The same "accepted for now, tracked as a known limitation" treatment Volume-3's Investigation Timeline used for its own read-time-merge-not-true-pagination limitation applies here.

## `PLATFORM_ANALYTICS_EXPORTED` — never added, mirroring Volume-3's `IMPERSONATION_STARTED` precedent

§8 names `PLATFORM_ANALYTICS_EXPORTED` as an event this volume should emit, but §9's Analytics Dashboard route is a single `GET /platform/analytics` — no export variant exists anywhere in the approved API surface for it to fire from. Rather than add an event with no code path that ever emits it, this event was left out of `domain-events.ts` entirely, the identical resolution Volume-3 used for `IMPERSONATION_STARTED`/`ENDED` when §9's route table gave them nothing to attach to. `COMPLIANCE_REPORT_EXPORTED`, by contrast, has a real, exercised route — `GET /platform/reports/export?type=COMPLIANCE` — and is emitted from exactly that call site.

## Compliance Dashboard: composed reads, two small Settings extensions, no new persistence

Every Compliance Dashboard widget reads from data that already exists, either in Volume-3's Support Session/Audit infrastructure or via two minimal, additive extensions to Settings' repositories (`ExportJobRepository.countByStatusAcrossWorkspaces`, `RetentionPolicyRepository`'s existing `findAll`, both exported from `SettingsModule` alongside the existing `SettingsService`/`AuditLogService` exports from Volume-3). `auditCoverage` is deliberately a raw count of `PlatformAuditEntry` records, not a percentage — a precise "% of events covered" formula would need a denominator (total events that theoretically should have been audited) this codebase has no way to compute cleanly, and a fabricated-looking percentage would be worse than an honestly-labeled count. `dataRetentionStatus` reports on Settings' real, enforced, per-workspace `RetentionPolicy` records — not the workspace-cancellation 90-day retention flow GTM-001/ADR-PLAT-001 mention, which turns out not to be encoded in the Workspace schema at all (a pre-existing gap, flagged during this volume's architecture review and tracked separately per the Architect's closing note, not fixed here).

### Failed Login Attempts: a genuinely new capability, closing a real security gap

Before this volume, Platform staff logins had zero failure-tracking — `PlatformAuthService.login()` never persisted a failed attempt, unlike tenant Identity's `LoginHistoryEntry`. `PlatformLoginHistoryEntry` (new collection, mirrors `LoginHistoryEntry`'s shape deliberately rather than reusing it — Platform authentication is a genuinely separate identity boundary, ADR-PLAT-002) is now written at every terminal branch of `PlatformAuthService.login()` — unknown email, wrong password, disabled account, and success — the same 4-branch shape tenant `AuthService.recordLoginAttempt()` already has. This is both what the Compliance Dashboard widget needed and a real, independently-valuable security improvement: a brute-force attempt against a Platform Super Admin account is now visible, where before it left no trace at all. Platform-side account lockout (mirroring `ADR-AUTH-001`'s tenant lockout policy) was not built — this volume's scope was tracking, not enforcement; lockout remains a distinct, unaddressed gap for a future volume.

## Platform KPIs: two formulas were engineering judgment calls, both confirmed by the Architect's approval

BR-006 ("Platform KPIs are calculated, never persisted") is the same live-aggregation discipline every Dashboard in this codebase already follows — no new decision needed there. Two of the six KPIs needed a formula invented, since the source document names them without defining one:

- **Platform Availability** — §4.5 names this without acknowledging §12 excludes Infrastructure Provisioning/SIEM, the categories real uptime monitoring would normally come from. Resolved as a derived proxy: `PlatformKpisService.computePlatformAvailability()` walks `PlatformAuditEntry` records for `PLATFORM_MAINTENANCE_ENABLED`/`DISABLED` in chronological order, sums the elapsed time inside any ENABLED→DISABLED (or ENABLED→now, if still open) interval as downtime, and reports `100 - (downtime / totalElapsedSinceFirstRecordedEvent) * 100`. This is explicitly _not_ infrastructure uptime — the returned `note` field says so in the response itself ("Application-level metric derived from recorded Platform Maintenance windows — not infrastructure uptime monitoring"), per the Architect's explicit instruction that "The metric shall be clearly labeled to avoid implying infrastructure monitoring capability." With zero maintenance history, it reports 100% rather than dividing by zero or returning `null` — a platform that has never recorded downtime is, by this metric's own definition, 100% available.
- **Feature Adoption** — resolved as % of active workspaces with a given flag enabled, computed by `FeatureFlagRepository.countEnabledAcrossWorkspaces()` (new method, Settings' `FeatureFlagRepository` also exported from `SettingsModule` for this purpose): explicit per-workspace `enabled: true` documents, plus every workspace with no explicit override for that flag if the flag's own default is `true`. This correctly accounts for the fact that most workspaces never touch most flags — a naive "count of explicit-enabled documents / total workspaces" would understate adoption for any flag whose default is already on (`CRM_MODULE`, `BILLING_MODULE`, `COMMUNICATION_MODULE`).

**Support Resolution Time** is computed as `updatedAt - createdAt` averaged across `RESOLVED`/`CLOSED` Support Tickets — an approximation, since `SupportTicket` (frozen, Volume-2) has no dedicated `resolvedAt` field and adding one for a single KPI wasn't judged to justify a frozen-schema change. A ticket that bounced back through `WAITING_CUSTOMER` before resolving would slightly understate its true resolution time under this approximation; documented here so a future reader doesn't mistake the gap for a bug.

## Security

`VIEW_COMPLIANCE` stays `PLATFORM_SUPER_ADMIN`-only (Architecture Review, 2026-08-10) — Compliance data (Failed Login Attempts, Break-Glass session detail) is materially more sensitive than aggregate analytics/KPI counts, so it sits at the same bar as `MANAGE_PLATFORM_POLICIES` rather than the broadly-granted `VIEW_PLATFORM_ANALYTICS`/`EXPORT_PLATFORM_REPORTS`, both `FULL` for all three roles per the Architect's explicit table.
