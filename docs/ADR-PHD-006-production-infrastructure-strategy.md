# Production Infrastructure Strategy

**Status:** Accepted
**Date:** 2026-08-17
**Scope:** PHD-001 Volume-3 (Performance, Scalability & Production Infrastructure) — the deployment/infrastructure half of the volume: Docker multi-stage builds for all three apps (`api`/`web`/`admin`), graceful shutdown, structured startup failure handling, `docker-compose.prod.yml`'s resource limits and healthcheck topology. See `docs/ADR-PHD-005-performance-scalability-strategy.md` for the application-level half of the same volume.
**Implemented in:** `docker/{api,web,admin}.Dockerfile`, `docker-compose.prod.yml`, `apps/api/src/{main.ts,tracing.ts,common/observability/tracing-shutdown.service.ts}`, `package.json` (root)

## Why this volume's own explicit mandate mattered: nothing here had ever actually been built via `docker build`

Every prior PHD-001/FRD-001 volume verified the running Node process directly (`pnpm dev:*`, or a manually-started `node dist/main.js`) — never a full containerized build. This volume's own mandate ("Docker healthchecks must be verified against actual container state," image sizes recorded before/after) required actually running `docker build`/`docker run` for the first time in this engagement's history, and doing so surfaced a cascade of real, previously-undiscovered packaging bugs across all three Dockerfiles — none hypothetical, all caught only because the build was actually executed rather than assumed correct. What follows documents the final, verified state; `docker/api.Dockerfile`'s own inline comments carry the detailed history of each bug for anyone debugging a regression later.

## The API image: from "never successfully built" to a verified, minimal production artifact

`docker/api.Dockerfile` bumps `node:20-alpine` → `node:22-alpine` (the root `package.json`'s pinned `pnpm@11.20.0` requires Node 22.13+'s built-in `node:sqlite` module — the build failed at the first `pnpm install` before this fix). A four-stage build (`deps` → `prod-deps` → `build` → `runner`) now produces a 552MB final image (down from 679MB unpruned; `node_modules` alone shrank 889MB → 313MB) by installing devDependencies only in the stages that need them (`deps`/`build`, for `tsc`) and resolving `@wapp/api`'s runtime dependencies fresh via a separate `--prod --ignore-scripts` install in `prod-deps`, rather than trying to prune a devDependency-inclusive install after the fact — `pnpm prune --prod` was tried and rejected twice in this exact workspace layout, since it deletes `apps/api/node_modules`'s own dependency symlinks entirely, not just devDependencies, while leaving the image no smaller.

The single most consequential bug found: `apps/api/node_modules/**`'s pnpm symlinks are **relative**, written assuming the exact original `/workspace/apps/api/node_modules/` directory depth. The Dockerfile's prior version flattened `apps/api/dist`/`node_modules` straight into `/app/`, silently breaking every such symlink's `../../` count — the build succeeded, but the running container crashed with `Cannot find module '@opentelemetry/sdk-node'`. The fix preserves the full original relative layout under `/app` (`/app/apps/api/dist`, `/app/apps/api/node_modules`, `/app/node_modules`, `/app/packages`) instead of flattening, so every symlink's relative depth stays exactly what it was when pnpm wrote it.

A `HEALTHCHECK` (previously absent from every Dockerfile in this repo) now targets `/api/health` via Node's own `http` module (no `curl`/`wget` added to the minimal runtime image) — version-neutral and unauthenticated by design (see `HealthController`'s own doc comment). `RUN npm install -g pm2` runs before `USER nestjs` drops privileges, not after — the prior ordering meant the image had never successfully completed a build at all (`EACCES` writing to `/usr/local/lib/node_modules` as an unprivileged user).

## Structured startup-failure handling: two compounding bugs, only found by actually killing Mongo

Must Fix #4's intent — a clean, structured `{"level":"fatal",...,"event":"bootstrap.failed",...}` JSON log line and a non-zero exit when `NestFactory.create()` fails (e.g. Mongo connection retry exhaustion) — initially appeared complete in code review but was never actually runtime-tested against a genuinely unreachable Mongo until this volume's own mandatory verification condition required it. Doing so found the implementation didn't work at all, for two independent, compounding reasons, each confirmed by reading `@nestjs/core`'s own source:

1. **`abortOnError` defaults to `true`.** A DI-instantiation failure during `NestFactory.create()` is caught internally by Nest's own `ExceptionsZone.asyncRun()`, logged via Nest's own `ExceptionHandler`, and terminated via `process.exit(1)` called directly from inside that internal teardown — never as a rejected Promise returned to the caller. The application's own `try`/`catch` around `NestFactory.create()` was structurally unreachable for this failure mode, full stop, regardless of anything else in the catch block. Fixed by passing `abortOnError: false`, which makes Nest's internal teardown `rethrow` the error instead, propagating it as a genuine rejection.
2. **Even with that fixed, output could still be lost.** Docker's stdout/stderr are piped, non-TTY streams; Node writes to them asynchronously, and `console.error()` immediately followed by `process.exit(1)` can terminate the process before the write actually flushes — a documented Node.js/Docker gotcha. Fixed by awaiting `process.stderr.write(...)`'s own completion callback before calling `process.exit(1)`.

Verified end-to-end via a live container test against an unreachable Mongo: the complete correct sequence now appears in container logs — Mongoose's own retry attempts (1)→(9), Nest's own `[ExceptionHandler]` diagnostic log, and finally the application's own structured `bootstrap.failed` JSON line, immediately before PM2 restarts the process. Both fixes were necessary; either alone would have left the gap.

## Graceful shutdown: one line unlocks four already-built mechanisms

`app.enableShutdownHooks()` (`main.ts`) was previously absent — without it, none of `onApplicationShutdown`'s hooks fire on `SIGTERM`/`SIGINT`: Redis's own `redis.quit()`, `@nestjs/bullmq`'s built-in graceful Worker close (waits for any in-flight job to finish before closing, no code of this volume's own needed to write that), and the OpenTelemetry SDK's flush all silently skip on every container stop. A related fix in `tracing.ts`: the OTel SDK previously registered its own standalone `process.on("SIGTERM", ...)` handler outside Nest's own shutdown sequence — replaced with a `TracingShutdownService implements OnApplicationShutdown` that participates in the same, single, ordered shutdown sequence `enableShutdownHooks()` now drives, rather than a second, independent signal handler racing it. Verified directly: `docker stop` against the running API container produces a clean SIGINT-driven exit code 0, not a forced kill.

## `docker-compose.prod.yml`: resource limits that are actually enforced, not just documented

Resource limits (`deploy.resources.limits.{cpus,memory}`) for all five services were added this volume, each overridable per-deploy via env vars, never hardcoded into application code. Given `deploy:` historically only applied under Docker Swarm, and WAPP's actual production topology is a single Hostinger VPS running plain `docker compose up` (TAD-001, no Swarm), this was explicitly verified rather than assumed: the installed Compose version (v5.3.1, matching this repo's `name:`-key Compose v2 syntax) correctly applies `deploy.resources.limits` to plain `compose up` containers' `HostConfig` — confirmed via a direct `docker inspect` probe against a throwaway container before relying on it for the real k6 load testing. `API_CPU_LIMIT`'s default was subsequently revised 1.0 → 2.0 based on k6 evidence — see ADR-PHD-005.

nginx's `depends_on` for all three app services was upgraded from a plain start-order dependency to `condition: service_healthy`, now meaningful for the first time since all three images finally carry a real `HEALTHCHECK` (previously none did). `web`/`admin`'s Dockerfiles both needed `ARG`/`ENV` declarations for `NEXT_PUBLIC_API_URL`/`NEXT_PUBLIC_APP_URL`/`NEXT_PUBLIC_ADMIN_APP_URL` — Next.js inlines these at **build** time, not read at runtime like every other env var, a gap that failed `next build` outright the first time it was actually attempted (prerendering any page reading one of these vars) and had been invisible until this volume's build-verification mandate.
