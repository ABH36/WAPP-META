# Observability Strategy

**Status:** Accepted
**Date:** 2026-08-13
**Scope:** PHD-001 Volume-2 (Observability, Monitoring & Logging) — distributed tracing, correlation-ID propagation, structured-log enrichment, error-reporting abstraction, and security-event logging. Covers the "how do we see what's happening across a request/job" half of the volume; the metrics/health/diagnostics half is ADR-PHD-004.
**Implemented in:** `apps/api/src/tracing.ts`, `apps/api/src/common/observability/*`, `apps/api/src/common/logging/logging.module.ts`, `apps/api/src/common/filters/http-exception.filter.ts`, every `apps/api/src/modules/*/queue/*.processor.ts`, `apps/web/src/{instrumentation.ts,lib/logger.ts}`, `apps/admin/src/{instrumentation.ts,lib/logger.ts}`

## OpenTelemetry auto-instrumentation, and why it actually works in this codebase's production build

`tracing.ts` is imported as the literal first line of `main.ts`, before any other module (including transitive ones) can `require` `http`/`mongodb`/`mongoose`/`ioredis`. `@opentelemetry/auto-instrumentations-node` patches those modules via require-in-the-middle — a technique that only works if the SDK's `start()` call genuinely happens before the target module is first loaded anywhere in the process. That precondition holds here specifically because `nest-cli.json` has no `builder: "webpack"` entry, so `dist/main.js` is a plain `tsc` output tree (one file per source file, real `require()` calls at the top of each), not a single bundled file — confirmed by reading the compiled output, not assumed. A webpack-bundled `main.js` would hoist/reorder requires in ways that could load `mongoose` before the tracing import runs, silently breaking auto-instrumentation in production while still working in `ts-node` dev mode. This is the kind of gap that only shows up after a `docker build`, not in local `pnpm dev`.

Provider-neutral by construction, not by convention: the SDK reads `OTEL_EXPORTER_OTLP_ENDPOINT`/`OTEL_SERVICE_NAME` itself (standard OTel env vars, zero custom plumbing), and falls back to a `ConsoleSpanExporter` in development when no endpoint is set — fully inert (no exporter at all) in production when unset, so an unconfigured deploy doesn't silently spam stdout with span dumps. `ConsoleSpanExporter` is imported as `import { NodeSDK, tracing } from "@opentelemetry/sdk-node"` then used as `new tracing.ConsoleSpanExporter()` — the installed version doesn't export it from `@opentelemetry/sdk-trace-node` at the top level the way older docs suggest; verified via direct `require()` introspection rather than assumed from documentation.

BullMQ has no official OpenTelemetry auto-instrumentation package (confirmed during Architecture Review) — every queue job gets a manual `tracer.startActiveSpan("queue.<name>", ...)` span instead, via `ObservableProcessor` (below). `webhook-delivery.processor.ts` additionally wraps its outbound `fetch()` call in its own child span (`webhook.delivery.http_request`) per the Architect's explicit callout that Webhook Delivery needed its own trace target distinct from the job-level span.

## The shared context problem: one `AsyncLocalStorage` singleton, not resolved through Nest DI

The Architecture Review named "a shared context mechanism" for correlation IDs. The naive approach — inject a request-scoped service everywhere — doesn't reach Pino's `mixin` hook, which fires on _every_ `Logger.log()` call throughout the service layer, not just the one HTTP access-log line `pinoHttp.customProps` can decorate. `mixin` has no access to Nest's DI container; it needs something it can read directly and synchronously.

The design: `request-context.storage.ts` exports a bare `AsyncLocalStorage<RequestContextStore>` module-level singleton — deliberately _not_ wrapped behind `@Injectable()` at that layer. `CorrelationContextService` (the thing actual call sites inject) is a thin wrapper around the same singleton, giving normal DI-friendly ergonomics (`run()`, `getCorrelationId()`, `getOrCreateCorrelationId()`, `setUserContext()`) to everything except `logging.module.ts`'s `mixin`, which imports `requestContextStorage` directly and reads it on every single log call:

```
mixin: () => {
  const store = requestContextStorage.getStore();
  return { service: "wapp-api", correlationId: store?.correlationId, userId: store?.userId, workspaceId: store?.workspaceId, platformUserId: store?.platformUserId };
}
```

`CorrelationMiddleware` seeds the store for the lifetime of an HTTP request (generating `X-Correlation-ID` when absent, propagating it when present — same pattern `genReqId` already used for `X-Request-ID`). `RequestContextInterceptor` (runs after guards, since that's when `request.user`/`request.platformUser` first exist) mutates the _live_ store object in place via `setUserContext()` — a documented, supported `AsyncLocalStorage` pattern (`getStore()` returns the real reference, not a snapshot), so identity discovered partway through a request becomes visible to every log line for the rest of that request, not only ones written after the guard ran syntactically.

`setUserContext` reads `AuthenticatedUser`/`AuthenticatedPlatformUser` per request — never both; a request is authenticated as a tenant user or a platform user, never simultaneously, so the interceptor's `if (request.user) {...} else if (request.platformUser) {...}` branch is exhaustive by construction, not an arbitrary priority order.

## `ObservableProcessor<T>`: one base class instead of 11 hand-rolled copies

Three separate approved Architecture Review findings — correlation-ID propagation into jobs, manual OTel spans for BullMQ, and execution-time/retry/permanent-failure metrics — all land on the same code path (every `process()` override) in every one of this codebase's 11 BullMQ processors. Rather than land three separate diffs across 11 files, `ObservableProcessor<T extends Partial<JobContext> = JobContext>` is an abstract `WorkerHost` subclass with a `final`-in-spirit `process(job)` that wraps correlation context + a `queue.<name>` span + duration/retry/permanent-failure metrics around an abstract `handle(job)` that subclasses implement instead of overriding `process()` directly. See ADR-PHD-004 for the metrics half of this class; this ADR covers only the tracing/correlation half:

- `job.data.correlationId ?? randomUUID()` — reuses the ID an HTTP request enqueued the job with (via `withCorrelationId()`, `job-context.util.ts`), or mints a fresh one when the job has none.
- A repeatable job's `data` is a fixed template set once at `queue.add()` registration time in each processor module's `onModuleInit()`, reused verbatim by every future tick. Baking a correlation ID into that template would freeze one ID across the job's entire lifetime — every future tick would misleadingly share the same trace. The fix is the absence of a change: the 6 self-triggered sweep processors (retention cleanup, subscription/invoice/support-session lifecycle sweeps, etc.) deliberately never call `withCorrelationId()` at their own enqueue site, relying on `ObservableProcessor`'s own per-invocation fallback to generate a fresh, correct ID on every tick instead.
- `span.recordException`/`setStatus(ERROR)` on failure, `span.end()` unconditionally in a `finally`, so a span is never left open on an unhandled rejection.

## Error reporting: the abstraction is the scope, not a vendor SDK

§4.5 approved "support external providers... provider selection remains environment-driven," read alongside §5's explicit exclusion of any actual vendor deployment (Sentry/Datadog/etc. are out of scope this volume). `ErrorReportingService` is an abstract class with one method, `captureException(error, context?)`; `NoopErrorReportingService` is the only concrete implementation today, registered in `ObservabilityModule` via `{ provide: ErrorReportingService, useClass: NoopErrorReportingService }`. Every real call site (`HttpExceptionFilter`'s non-`HttpException` branch, `main.ts`'s `uncaughtException`/`unhandledRejection` handlers) depends on the abstract class, never the concrete implementation — a genuine future integration is one new class swapped into that provider factory, with zero changes anywhere else.

`NoopErrorReportingService` logs at `debug`, not `error` — a deliberate correction made mid-implementation. Every real call site already logs the same exception at `error` severity through its own `Logger` before or alongside calling this; logging it again here would duplicate every unexpected-error line in production. `debug` is invisible in production (which runs at `info`, per `logging.module.ts`) but confirms locally that the call site is wired and reachable.

`main.ts` gained `process.on("uncaughtException"/"unhandledRejection")` handlers: log full detail, call `errorReporting.captureException()`, then `process.exit(1)`. Deliberately not a "log and keep serving" handler — Node's own guidance is that a process's state after an uncaught exception is undefined, and a container orchestrator restarting a crashed process is a known, bounded failure mode; a Nest app instance limping along in a corrupted state serving unrelated requests is not.

## Security event logging: extends a frozen precedent instead of inventing a new one

New signals this volume — permission denials (`PermissionsGuard`/`PlatformPermissionsGuard`), rate-limit violations (`HttpExceptionFilter`'s new `ThrottlerException` branch), inbound webhook signature failures (`WebhookController`) — needed a design decision: a new domain event routed through the existing Audit/Notification/Analytics event-driven integration standard, or a structured log line plus a Prometheus counter only.

`domain-events.ts`'s own doc comment already establishes the answer for a directly analogous case: Identity's own security signals (login success/failure, session revocation) deliberately stay _outside_ the event-driven audit-log projection — "Settings orchestrates Identity via direct service calls, not event projection." These new security signals are the same class of thing (Identity/Platform/Communication's own internal security posture, not a business-domain state change another module's audit trail needs to react to), so the same reasoning applies: structured log (`logger.warn`) plus a Prometheus counter (`securityPermissionDeniedTotal`/`securityRateLimitViolationTotal`/`securityWebhookSignatureFailureTotal` — see ADR-PHD-004), no new domain event, no duplicate Mongo audit write. Extending an already-Architect-approved precedent rather than inventing a parallel pattern keeps these two related decisions consistent instead of silently diverging.

## Frontend: Next.js's own two hooks, not a forced Edge-runtime Pino

apps/web/apps/admin needed "the same Pino/structured standard" apps/api already had. Next.js's App Router exposes exactly two general-purpose server-lifecycle hooks — `instrumentation.ts`'s `register()` (fires once at server boot) and `onRequestError()` (fires for every server-side error in Server Components, Route Handlers, and Middleware). `src/lib/logger.ts` in each app is a `pino` instance matching `logging.module.ts`'s shape: JSON in production, `pino-pretty` in development, the same class of sensitive-field redaction, `service: "wapp-web"`/`"wapp-admin"`.

The one real constraint: Middleware runs on the Edge runtime by default, and Pino's core depends on Node built-ins the Edge runtime doesn't provide — a top-level `import pino` reachable from `instrumentation.ts`'s shared module would break the Edge bundle. Both hooks branch on `process.env.NEXT_RUNTIME === "nodejs"` (the documented, version-accurate way to detect which runtime is actually executing) and only then `await import("./lib/logger")` — the same dynamic-import-behind-a-runtime-check pattern Next.js's own docs use for cross-runtime instrumentation (Sentry, etc.). The Edge branch falls back to a structured `console.error(JSON.stringify(...))` line instead — still JSON, just not through the Pino instance, since Pino genuinely cannot run there. Verified by actually running `next build` for apps/web and confirming a clean compile with no Edge-bundling errors, not assumed from reading the pattern in Next's documentation alone.

`middleware.ts` itself is untouched — it's a pure routing gate (protected/guest-route redirects) with no logging needs of its own; forcing structured logging into it would mean fighting the Edge-runtime constraint for no real benefit, since Next's own `onRequestError` hook already covers Middleware's error path from the Node-runtime side of `instrumentation.ts`.
